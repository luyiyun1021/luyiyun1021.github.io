    主题

    1. 大模型推理基础概念, 为什么需要有kv cache, prefix cache

    2. kv cache, prefix cache在推理引擎中的实现和用法

    3. 推理引擎接入attention store后的改动

    常见的LLM模型结构 (以LLaMA为例)

    模块 作用
    Embeddings 把输入 token id 映射成 hidden_dim 长度的向量。
    RMSNorm 用均方根归一化当前隐藏状态，稳住数值并让层与层之间梯度更平滑。
    Self-Attention 计算 token 之间的自注意力
    Residual Add (+) 将注意力输出叠加回输入张量，构成残差连接。
    Feed-Forward 线性层负责隐藏维度扩展, 表征复杂特征
    SwiGLU 激活函数, 给模型带来非线性
    Linear → Vocab → Softmax 把隐藏向量投影到词表维度，得到每个 token 的 logits。再通过 Softmax算出概率

    Self-Attention

    Self-Attention

    自注意力机制允许模型将词与其他词关联起来。

    假设我们考虑一个序列长度为6, embedding维度为512的输入, 由于是自注意力, QKV都是相同的

    softmax(QKTdk)softmax(\frac{QK^T}{\sqrt{d_k}})softmax(dk​​QKT​)捕捉了两个token之间的相关性

    上一步的结果再和V做矩阵乘, 得到与输入维度相同的输出矩阵, 每行(即经过计算后的的新的embedding)不仅捕捉了词语的含义（由嵌入表示）或在句子中的位置（由位置编码表示），还捕捉了每个词与其他词的相互作用。

    KV cache

    Next Token Prediction Task

    首先来了解一下LLama的训练（下词预测任务）：seq2seq的生成，但迭代T次，seq_len逐渐增加。

    即输入序列的第一个token将映射到输出序列的第一个token, [SOS] -> Love, 第二次迭代中将用[SOS] Love预测that, 以此类推

    Motivation behind KV cache

    在推理的每一步，我们只关心模型输出的最后一个词元，因为我们已经有了之前的词元。然而，模型需要访问所有之前的词元来决定输出哪个词元，因为它们构成了模型的上下文（或称为“提示”）。
    有没有办法让模型在推理时对已经看到的词元进行更少的计算呢？

    KV cache

    下句预测时的Self-Attention：

    • timpstep=1时seq_len=1，给[SOS]时，预测Love；

    • timpstep=2时seq_len=2，给[SOS] 和 Love时，预测that

    • timpstep=4时seq_len=4，给[SOS] 和 Love 和 can 和 quickly时，预测seize…

    再来分析一下，每次个timestep的self-attention中我们到底需要哪些：因为我们只关注最后一个token的**attention_output**，如下图timestep=4，我们只需要attention_output的第4个token。

    因此我们只需要Q的最后一个token和K的所有token相乘，得到最后一个token的attention_score，然后用V的所有token再与attention_score点积(相乘求和)，得到最后一个token的attention_output：

    由上分析可知，每个timestep，我们的Q只需要新增的那个token即可，而K和V要缓存之前timestep的token，保证token是全的。每次计算出来的attention_output就是那个新增的token的attention。 这样就可以节省大量计算开销。

    参数量的计算方法: 分析transformer模型的参数量、计算量、中间激活、KV cache

    KV Cache占用的显存空间

    Q, K的形状为:[b,head_num,s,per_head_hidden_size], 那么对于每个decoder layer，每个 token 的 K、V 矩阵都是 embedding_size=num_heads * head_size，再乘上 seqlen和 batch size，那就是每个layer的 kv Cache 所需的存储容量了。

    例如，在 LLaMA 2-13B 中，head_num = 40, layer_num = 40, dimension = 5120, 对于1个token的 KV Cache 一共需要 2 (key and value vectors) × 5120 (hidden state size) × 40 (number of layers) × 2 (bytes per FP16) = 800KB。

    以模型支持的最大的上下文长度4096为例，对于4096个token, 需要800KB * 4096 = 3.2GB的KV cache, 每增加一个batch则需要3.2GB显存，对于一张A100 40GB来说，在加载完模型26GB之后，余下的显存也仅能支持4个batch

    优化方向

    • 模型: 减少hidden size(比如deepseek的MLA架构), 量化(减少单个元素储存空间, 比如fp16 -> fp8)

    • 架构: prefix cache(kv cache复用)

    KV Cache能省下的FLOPs

    FLOPs，floating point operations，表示浮点数运算次数，衡量了计算量的大小。
    如何计算矩阵乘法的FLOPs呢？
    对于 A∈R1×n,B∈Rn×1 ，计算 AB 需要进行 n 次乘法运算和 n 次加法运算，共计 2n 次浮点数运算，需要 2n 的FLOPs。对于 A∈Rm×n,B∈Rn×p ，计算 AB 需要的浮点数运算次数为 2mnp 。

    • Attention 部分总计算量

      • (8 * seqlen * embedding size^2 + 4 * seqlen^2 * embedding size) * layer_{num} = 8 * 4096 * 5120 * 5120 * 40 + 4 * 4096 * 4096 *5120 * 40 = 48 T FLOPS

    • Q、K、V 矩阵计算

      • 原先一共需要 3 (Q+K+V) * 2 (mul+add) * embedding size * embedding size * seqlen * num_layer计算量

      • 现在一共需要 3 (Q+K+V) * 2 (mul+add) * embedding size * embedding size * num_layer计算量

      • 省了 3 * 2 * 5120 * 5120 * (4096 - 1) * 40 TFLOPs的计算量

    • Attention Score部分

      • 原先一共需要 2 (mul+add) * embedding size * seqlen * seqlen * num_layer计算量

      • 现在一共需要 2 (mul+add) * embedding size * seqlen * num_layer计算量

      • 省下 2 * 5120 * 4096 * (4096 - 1) * 40 TFLOPs的计算量

    • Attention Score * v部分

      • 原先一共需要 2 (mul+add) * embedding size * seqlen * seqlen * num_layer计算量

      • 现在一共需要 2 (mul+add) * embedding size * seqlen * num_layer计算量

      • 省下 2 * 5120 * 4096 * (4096 - 1) * 40 TFLOPs的计算量

    • attention 后的线性映射

      • 原先一共需要 2 (mul+add) * embedding size * embedding size * seqlen * num_layer计算量

      • 现在一共需要 2 (mul+add) * embedding size * embedding size * num_layer计算量

      • 省下 2 * 5120 * 5120 * (4096 - 1) * 40 TFLOPs的计算量

    • 计算量从48 T FLOPS -> 48/4096 TFLOPS, 节省99.98%计算量

    使用KV Cache后推理逻辑的变化

    当不使用 KV cache 时，每次生成下一个 token 的注意力计算都会对整条已生成序列（seq_len）进行自注意力计算。
    而使用 KV cache 后，在生成新 token 时不需要重新计算所有先前 token 的 Key/Value 表示，只需对当前新生成的 token 计算 Query，并与已缓存的 Key/Value（即 KV cache）进行一次点积操作，得到注意力分布，从而减少计算量。此时，注意力的输出序列长度从整个历史序列长度缩减为 1（仅对当前 token 的预测所需）。

    因此, 每层 Decoder 都会接收到一个长度为 seq_len 的张量, 尽管输入的长度为 1，但注意力层并非只对这 1 个 token 做内部计算后结束。因为我们已经缓存了所有之前步骤（token）的 Key 和 Value，因此在注意力计算时，当前生成的 token 的 Query（Q）会与已经缓存的（seq_len-1）个 Key/Value 一起作用，从而模拟完整上下文的自注意力过程。换句话说：

    • Query 是当前新 token 对应的 Q（长度为1的Q）

    • Key/Value 则来自于之前缓存的所有历史 token（长度为过去累积的序列长度）

    因此，尽管这一轮输入激活只有一个 token，但注意力计算仍然是对所有历史信息进行查询（Q对缓存的K/V），确保模型没有丢失上下文。

    Prefix Cache

    在讲 RadixAttention 之前有必要简单讲一下 Prefix Cache：

    明显这两个 Prompt 都有共同的很长的前缀，如果我们把 Prompt 中共同的前缀产生的 KV Cache 给缓存下来，无疑会极大的减少 Prefill 阶段的时间从而减少 TTFT，并且如果不缓存，这个共同前缀的 KV Cache 将会被存两次，导致浪费显存，因此缓存下来还能减少显存从而增大吞吐

    这就是 Prefix Cache 所做的事情：将共享前缀的 KV Cache 给缓存起来，并且是一个能无损同时增加 TTFT 和吞吐的技术

    为什么只有共同前缀的KV cache能复用

    考虑 ”你好百度“ 和 “再见百度” 两个请求, 正在通过度这个词预测下一个字,

    第1层: 度的kv cache是由input embedding * K, V 参数矩阵得到的, 度的input embedding是由词表映射(这个是固定的)和位置编码(这个可能一样, 也可能不一样, 比如你好百度和百度你好)叠加的, 因此两个度的input embedding可能不一样, 如果input embedding是一样的, 那么度的kv cache是一样的,

    第2-n层: 度的kv cache是由input embedding * K, V 参数矩阵得到的, 度的input embedding是由上一层的输出和位置编码叠加的, 回顾上一层的Attention计算, q需要和历史的所有kv计算得到q和上文所有token的分数, 乘上上文所有v的值, 因此上一层的输出取决于所有上文内容, 因此如果请求的前缀不相同, kv cache不能复用

    Radix Cache

    上面的 Prefix Cache 有这么几个问题还没有说明：

    • 怎么实现？用什么数据结构存储这些 Prefix Cache？

    • 你要存多少个 Prompt 的 KV Cache？存满了该怎么办？

    RadixCache 相比于上述提到的 Prefix Cache，引入了树(Radix Tree)结构来进一步增强 Prefix Cache（如何管理前缀 token）。

    • Radix Tree最大的特点就是，它的node，不仅可以是一个单独的元素，也可以是一个变长的序列。具体体现在，在必要的时候，一个已经在Tree中的大node可以动态地分裂成小node，以满足动态shared prefix的需求。

    • RadixCache 提出使用 LRU 策略来管理前缀树，具体来说就是 Prefix Cache pool 大小有限（显存有限），因此存到一定数目的 Prefix 的 Cache 后可以根据 LRU 策略来驱逐，从而在不至于打爆 Prefix Cache pool 的基础上还能拥有更大的 Cache hit rate。

    RadixCache LRU 策略示例：

    步骤(1)，Radix Tree最初是空的。步骤(2)，服务器处理传入的用户消息: “Hello”，并使用LLM输出: “Hi”，进行响应。system prompt为: “You are a helpful assistant”、用户的prompt为: “Hello!”，LLM回复为: “Hi!”；整个对话被合并为一个大node，保存到Radix Tree的节点a。步骤(3)，同一个用户输入了一个新的prompt，服务器从Radix Tree中找到的历史对话前缀(即对话的第一个回合)并复用它的KV Cache。新回合作为新节点追加到树中。步骤(4)，开始一个新的聊天会话。Radix Tree将(3)中的大节点“b”，动态地拆分为两个节点，以允许两个聊天会话共享system prompt。步骤(5)，第二个聊天继续。然而，由于内存限制，(4)中的节点“c”必须被清除。新的对话被缓存到新的节点"d"。

    sglang 的 kv cache 管理相关模块

    KV Cache与内存池

    我们先来介绍一些管理KV Cache的关键组件。我们用两级内存池来管理KV Cache：

    1. req_to_token_pool

    • 用途： 将Request映射到其token的 KV cache的索引。

    • 形状： 最大允许Request数（通过 max-running-requests 设置） * 最大允许 token 数（通过 model_config.context_len 设置）

    • 访问：

      • Dim0: req_pool_indices

      • Dim1: 每个token在Request中的位置(0, 1, 2, …)

      • 返回值：token 在 token_to_kv_pool 的 cache_loc

    2. token_to_kv_pool

    • 用途： 进一步将单个token从它的KV cache索引映射到其实际的KV cache数据。对于不同的注意力机制（如MHA、MLA、Double Sparsity），token_to_kv_pool可能有不同的实现。

    • 形状： 层数 * 最大允许 token 数 * attention头数 * 每个attention头的维度

    • 访问：

      • Dim0：layer_id，该kv cache对应的层数

      • Dim1：out_cache_loc，token对应的kv cache索引（req_to_token_pool的返回值）

      • Dim2：注意力头

      • Dim3：注意力头维度

      • 返回值：cache_k & cache_v：实际的 KV cache数据

    3. tree_cache

    • 用途： tree_cache是一个树结构，用于加强跨Request之间的prefix KV cache复用。tree_cache 负责为每个请求在token级别更新req_to_token_pool 和 token_to_kv_pool。一个token在 tree_cache、req_to_token_pool 和 token_to_kv_pool 之间的数据可以通过其KV Cache 索引 (out_cache_loc) 相互映射。

    • 访问：

      • 键：Token List。

      • 值：Token List的 KV cache索引 List

    Sglang RadixCache 具体实现

    RadixCache = 带节点引用计数的前缀-KV 索引树, 它把 token id 序列 → KV-cache 索引 的映射组织成一棵前缀树（radix tree）；请求运行时只保留自己还在用的路径的引用计数（lock_ref > 0），其余节点可被 LRU 驱逐并把显存归还给 KV-memory pool。

    1 整体动机

    需求 RadixCache 提供的能力
    kv-cache 重用：两条请求共享前缀，就不要重复存 KV。 相同前缀的 token 序列合并到一条根-到-节点路径，value 存 kv 索引张量。
    显存可回收：已结束或被截断的前缀应及时释放。 lock_ref 记录“仍被多少活跃请求引用”；evict() 只逐叶删除 lock_ref==0。
    page 对齐：为配合分块 KV 通信，可按 N token 为一页对齐。 page_size 决定一次比较/插入的 token 步长，默认 1；大于 1 时按页存键。

    2 核心数据结构

    • 根节点 key = [] , value = [] , lock_ref = 1（永不驱逐）

    • 压缩前缀树：相邻节点的 key 无重叠；从根到叶的 key 串联就是完整 token 序列。

    3 分页机制

    paged_token_to_kv_pool_allocator是社区最近merge的功能，旨在将所有KV Cache按照page维度（概念同as的block）切分管理，空间的分配、释放以及读写都按照block维度进行

    4 引用计数

    时机 调用 作用
    请求 被调度执行，持有前缀 inc_lock_ref(node) 把从该节点到根的锁 +1；如果这是从 0 → 1，则 evictable_size_ 减少。
    请求 被释放 / 截断 dec_lock_ref(node) 对应减回，0 → 1 以外不动 evictable_size。

    5 API

    5.1 match_prefix(key: List[int]) -> (Tensor, last_node)

    1. 沿树匹配最长公共前缀

      • key_match_fn = 逐 token 或逐 page_size 比较

      • 遇到「部分匹配」时会 _split_node

    2. 返回

      • value＝所有匹配节点的 value 拼接（即已存在的 kv 索引）

      • last_node＝匹配到的最后节点（可能是新加的 split 节点）

    5.2 insert(key, value)

    把token_ids按page对齐后和他们的KV indices插入到Radix Cache中。如果成功，会返回一个新的prefix长度（new_prefix_len）

    5.3 cache_finished_req(req) v.s.cache_unfinished_req(req)

    请求完全结束 v.s. 请求未结束：

    1. 拿出这条请求的完整的上下文token list(origin_input_ids + output_ids)及 kv 索引按page对齐后写入 RadixCache (insert)

    2. 归还插入过程中新增的共享前缀部分到 token_to_kv pool

    3. 调整节点引用计数

      • cache_unfinished_req

        调用match_prefix()更新Request的prefix_indices和last_node。这里非常重要，因为prefix_indices和last_node在下一个decode的迭代会被用到。

        • prefix_indices用于计算需要extend/prefill的token数。

        • last_node用来在更新lock的时候回溯到root节点。

        内存安全管理-为了防止意外删除活跃的cache节点，我们用一个锁来保证使用中的节点不被释放。在上述状态转换之后，旧的last_node通过dec_lock_ref()解锁，允许它在不再需要的时候被释放。新的last_node被锁定，防止被意外删除。

      • cache_finished_req

        把 req 在 Req-token pool 里的 slot 释放同时对它曾经锁住的树节点做 dec_lock_ref

    5.4 evict(num_tokens)

    • 先 heapq.heapify(所有叶节点)，按 last_access_time 作最小堆

    • 反复弹出最久未用且 lock_ref == 0 的叶子

      • free(leaf.value) → 还显存

      • self._delete_leaf()：从父删引用；若父变成新叶，再入堆

    • 直到腾出 num_tokens 或已无可驱逐节点

    调用时机

    # 调用点（函数栈） 代码触发条件 典型场景
    1 Prefill / Chunk-Prefill 申请新 KV 空间时ScheduleBatch.prepare_for_extend → alloc_token_slots(*) / alloc_paged_token_slots_extend → **tree_cache.evict(num_tokens)** token_to_kv_pool_allocator.available_size() < 待写入 token 数 刚把一批新 prompt 切成 chunk，要塞进 KV 缓存，但显存不够，所以先淘汰最旧、无人引用的页。
    2 Decode 下一步前的容量检查ScheduleBatch.check_decode_mem → **tree_cache.evict(pages_needed)** deocde 阶段update_running_batch 长句子持续解码，或者连续 batching，KV 越来越满——先清理可回收页，再继续解码。
    3 Retract Decode 回退时ScheduleBatch.retract_decode 循环里
    ① 释放被回退 req 的 KV
    ② **tree_cache.evict(residual_size)**    		 已经释放了一些页，但还不足以满足 “每条 req 至少还能再解 N 步” 的预算 超大并发或多路长文本 decode，显存吃紧 → 调度器弹出若干历史最旧请求并回收其页。

    类别 RadixCache AsRadixCache 新增 / 改动 作用
    初始化 只保存 CPU/GPU 端内存池指针 self.layer_ids保存模型层数 + ref_ascli() 持有 AttentionStoreSDK 句柄 后续读写 KV 时需要告诉 AS 哪几层
    match_prefix 只查本地 radix-tree ① 正常从本地匹配
    ② 如果本地命中长度 < key, 调用_as_match_and_read() 到 AS 增量回填 KV，再把新数据插进树    		 1. sglang在给请求分配kv cache空间时，会调用asradix cache的match_prefix接口

    2. 在asradix cache的match_prefix接口中，同步调用一次as agent的match接口，判断能否从as获取从start_match_block_index开始的kv cache

    3. 如果AS有cache命中，就从token_to_kv_pool分配空间，然后调用AS读接口读取kv cache

    4. 读取成功后，更新索引
    cache_finished_req 写 radix-tree → 释放 pool 除原逻辑外：
    · 将整条 token →page 映射flush_token_index() 推给 AS    		 写：生成结束时把radix cache中的索引完整同步到 AS

    “索引” 新增 / 持久化 —— 告诉 AS, 这些 token 对应的 KV 现在已经保存在本地 HBM，Block ID 如索引所示，AS 可以把它们当作“已缓存”来命中。
    cache_unfinished_req 把当前已 prefill 的部分挂到树里 保持原逻辑
    evict LRU-heap 找叶子 → 释放 KV ① 额外整理出被驱逐 page 的 完整 token 序列 & blockID② 调 flush_token_index() & write() 通知 AS 失效 / 搬运数据 驱逐时更新:

    1. “索引” 失效 —— 告诉 AS：整条序列 token_ids从 start_flush_block_index 这个块起，后面的 KV 已被驱逐，只剩下前缀仍在本地；后缀如果要用必须去 AS 拉取。

    2. “值” 写入 —— 把显存里整条序列 token_ids真正的 KV Tensor 块从 start_flush_block_index 这个块起拷到 AS
