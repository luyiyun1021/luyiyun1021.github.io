DeepSeek 中的专家均衡分析与优化

发表于 2025-08-20 分类于 大模型 ， 推理技术 ， Deepseek优化 阅读次数： 本文字数： 3.9k 阅读时长 ≈ 14 分钟

Deepseek MoE

  • MoE是什么？

    • Mixture of Experts,混专家模型

    • 共享专家+{Router/Gate+路由专家}+加和

  • 为什么要有MoE?

    • 相同模型参数情况下大幅降低计算量

  • Deepseek V3/R1 MoE的关键参数

    • 61层中有58层包含MoE层

    • 每个MoE层包含1个共享专家和256个路由专家

      • 每层每个专家参数量约44M,256x58层累计约656.6B

    • Router/Gate的选择策略

      • 256个路由专家分为8组，每组32个

      • 每组选择最大2个得分进行求和，作为组得分

      • 选择组得分最高的4组

      • 从上述4组中得分最高的8个专家

EP并行与负载均衡

负载不均的原因

  • deepseek模型本身存在不均（天然热点专家）

  • 不同batch的token专家选择的随机性

负载均衡的衡量指标及对性能的影响

  • Token数峰均比：每一次MoE层 Dispatch中所有rank 最多处理 token数/平均处理 token数

  • 不均衡度：一段时间内 Token数峰均比平均值，1表示完全均衡，越大越不均衡

Prefill 双流Moe=2(Dispatch+Combine)处理总时延 35.6ms

  • Prefill 1个Token处理总时延0.16us(RDMA收发+NVLINK收发)

  • 不均衡度增加0.1，多处理6260token,时延增加2x1.05ms(6%↑)

Decode 双流Moe=2(Dispatch +MLP + Combine)处理总时延1.42ms

  • Decode 1个Token 处理总时延0.7us(RDMA收发+MLP计算*)

  • 不均衡度增加0.1，多处理102个token,时延增加2x0.07ms(10%↑)

EP负载均衡-静态冗余策略

运行中

方案1

  • 各Rank维护自身发送到各个路由专家的token数（逐次累加）

  • Rank0接收中控的重排请求（定时/监控吞吐变化），通过All-Reduce获取所有Rank/专家的累积计数，即该专家的权重

  • 采样统计->全量统计，吞吐性能20%+

方案2（减少通信量）

  • 每个Rank维护本地专家接收Token的累积计数

  • 然后通过all gather获取一段时间的累加和

停流

负载均衡算法EPLB确定部署方案

  • Prefill EPLB

  • Decode EPLB

停流，加载新的专家权重，接入新流量

  • 将专家权重预加载到Host DDR

  • 重排后再按需加载到GPU HBM

  • 58x4专家理论耗时约200ms, 实测预加载耗时600ms

运行中

  • 逻辑专家/物理专家

  • 部署数/映射表/反映射表

EP负载均衡-EPLB算法

EPLB算法

  • 输入：专家总数(256加冗余)+256个逻辑专家的权重+rank数+节点数+组数(deepseek中为8)

  • 输出：

    • (256加冗余)个物理专家->256个逻辑专家的映射表

    • 256个逻辑专家->(256加冗余)个物理专家的映射表

    • 256个逻辑专家的部署个数（至少为1，有冗余的大于1）

  • 算法目标：让每个Rank分到的多个专家的权重和相对平均

分组负载均衡

  • 用于Prefill阶段(num_groups% num_nodes ==0)

  • 考虑机间机内的带宽差异和Prefill两阶段通信，将同组专家放在同一机器内

  • P4-EP32-32冗余:

    • 4机32卡，每卡9专家，共32个冗余专家

全局负载均衡

  • 用于Decode阶段(num_groups% num_nodes!=0)

  • 当前Decode MoE流量因为低时延需求，都走RDMA,因此不考虑专家分组的差异

    • D18-EP144-单卡2专家，共288物理专家，32冗余

    • D9-EP72-单卡4专家，共288物理专家，32冗余

    • D10-EP80-单卡4专家，共320物理专家，64冗余

EP负载均衡-Decode全局负载均衡

Step1:

  • 给每个逻辑专家预留1个部署

  • 通过削峰策略逐个确定部署哪个逻辑专家

**Step2:**将待部署专家组合部署到rank中，单rank 2/4个专家

贪心算法（排序+串行放置）

  • 基于[冗余后新权重]对待部署专家进行排序

  • 从权重最大的开始放置到rank,每次都选当前未满且已部署专家权重和最小的rank

贪食蛇算法（排序+并行放置）

  • 基于[冗余后新权重]对逻辑专家进行排序

  • 按照降序方式进行以贪食蛇方式放置

EP负载均衡-Prefill全局负载均衡

Step1:256个逻辑专家属于8个组（模型决定)，每个组将本组8个专家权重加和，得到组权重

Step2:通过贪心算法，将8个组放到4个node中

Step3:每个Node内实现全局负载均衡，64逻辑专家->72物理专家

Step4:每个node内72个物理专家通过贪心算法放到8个rank上

EP负载均衡-Dispatch Token均分

Hash均分

  • 每个Token计算HASH值，[HASH%部署数]确定目的rank

    • 优点：实现简单，能够并行计算

    • 缺点：存在HASH不均

RR均分

  • 每个rank通过RR方式分配token到多个物理专家

  • 不能均分的token基于src rank id确定目的rank

  • 优点：分配不均的上限为(rank数/2)

  • 缺点：有一定的算子开销（可接受）

EPLB算法详细解析

  • 项目源码：https://github.com/deepseek-ai/eplb

  • 项目简介：专家并行负载均衡器

  • 项目背景：在DeepSeek的LLM大模型中采用了MoE技术，MoE技术通过引入多个专家(Expert)增大模型的总参数量，而在单次训练或推理中只激活其中部分专家来降低计算量，从而平衡模型规模和算力需求。DeepSeek采用专家并行（EP）来提高MoE的处理性能，不同的专家被分配到不同的GPU上。不同专家的负载因当前工作负载而变化，在特定的EP-GPU部署策略下GPU可能会出现负载不均的问题，在水桶效应的作用下影响总体性能。正如DeepSeek-V3论文中所述，DeepSeek采用冗余专家策略来复制负载过大的专家，并通过估计专家负载的分布及算法计算出合理的专家复制和专家在GPU放置策略，来提升系统性能。

  • 项目概述：开源项目是关于一种基于特定分布给出专家复制和专家在GPU的放置策略的算法。估计专家负载的分布则一般采用历史统计的移动平均(moving average of historical statistics)得到，DeepSeek-V3论文中提到的统计时长为10分钟。需要指出的是，该项目只讨论了专家的部署策略，没有讨论在某种工作负载情况下如何基于当前专家的部署策略来分发工作任务给各个GPU，这点可能在DeepEP中有实现？已确定没有

  • 项目解读

    • 根据推理中Prefill和Decoder的不同需求分别实现了两种部署策略, 这两种策略的核心区别在于是否关心EP专家组

      • 分层负载平衡，适用于较小的专家并行规模(Prefill)，需满足EP专家组数(num_groups)可以被机器节点数(num_nodes)整除

      • 全局负载均衡，适用于较大的专家并行规模(Decode)

源码解读

入口函数

  • 函数输入

    • logical experts，逻辑专家，也就是MoE算法中提到的专家，DeepseekV3是256，其数量为num_logical_experts

    • physical experts，物理专家，也就是考虑复制之后的专家，其数量为num_replicas，需要是GPU卡数的整数倍

    • num_groups，EP组的数量

    • num_nodes，机器节点数

    • num_gpus，GPU的卡数，需要是节点数的整数倍，也就是单机2/4/8卡等

    • weight， 维度是 [layers, num_logic_experts]，也就是每一层中，每个逻辑专家的负载统计

  • 函数输出

    • physical_to_logical_map， [layers, num_replicas]，表示 每一层 每个物理专家位置上所对应的 逻辑专家号

    • logical_to_physical_map，[layers, num_logical_experts, X]， 表示每一层 每个逻辑专家 被映射到 哪些物理专家位置上

    • expert_count: [layers, num_logical_experts], 表示一层每个逻辑专家 对应的物理专家数量，确定了logical_to_physical_map的第三个维度X的大小

  • 中间函数输出

    • phy2log: [X, num_phy], logical expert id of each physical expert， 每一层 每个物理专家位置上的逻辑专家号

    • rank: [X, num_phy], the duplica rank， 每一层每个物理专家位置上的 复制的专家个数，没有复制专家的话为0

    • logcnt: [X, num_log], number of replicas for each logical expert，每一层 每个逻辑专家号的复制次数(物理专家数量)

分层负载均衡

  • 先将专家组平均打包到节点上 balanced_packing
