    Sglang 异步专家重排逻辑梳理

    发表于 2025-08-21 分类于 大模型 ， 推理技术 ， Sglang 阅读次数： 本文字数： 3.6k 阅读时长 ≈ 13 分钟

    0. 启动准备

    • Scheduler 启动时

      • 如果启用了 enable_redundant_experts，Scheduler 会拉起一个守护线程 async_update_weight_thread。

    • 线程一启动就调用

      • 这里的 model_name 通常是 "main"（还有 draft worker 时会再加一个 "mtp"）。
        mmap_infos = async_expert_loader.create_mmap(model_name, ep_rank, ep_size)

    • create_mmap 内部做了四件事

      • 拼出路径 /dev/shm/{name}_rank_{ep_rank}_ep_dyn.weights。

      • 若文件不存在：open(..., 'wb').close() 立刻创建空文件。

      • os.ftruncate 把文件扩展到预估的显存大小（TOTAL_MODEL_SIZE // ep_size + MAIN_MODEL_REDUNDANT_SHM_SIZE）。

      • mmap 再加 cudaHostRegister——把这块共享内存注册成可直接给 GPU DMA 的“pinned memory”。

      • 完成后返回的 mmap_infos 保存了 文件指针，供后续直接用 ctypes+frombuffer 建 Tensor 映射。

    • 此时文件已经在 /dev/shm 出现并定长，随后的

      • loading_model_weights_thread.save_tensor_to_shm_mem 只是 seek+写入；

      • GPU 端 load_tensor_from_shm_mem 只是 从已映射地址构 Tensor。

    • 等待接收loading_model_weights_thread发来的信息

    1 . 外部触发

    1. TokenizerManager 收到 HTTP→生成 RearrangeExpertsReqInput。

    2. 通过 ZMQ PUSH 把该对象广播给 所有 TP-rank 的 Scheduler。

    2 . Scheduler 入口

    • 只有 experts-rank 0（EP 0）真正起调度, 设置如下变量；其余 rank 直接返回 success 信息。

    3 . 事件环里的“双魔数”同步

    在 prepare_dp_attn_batch() 里，每轮都会 all_gather 一次各 rank 的num_tokens。Scheduler 借此塞入 2 个特殊值：

    魔数常量 作用
    CACULATE_EXPERT_MAGIC_NUM 通知大家：先去算新路由表
    REARRANGE_EXPERT_MAGIC_NUM 通知大家：权重已 OK，可以正式切

    4 . 第一次魔数 → 触发计算路由表

    execute_caculate_expert_rank_table()

    “把 **各 rank 最近的 token 统计 → 新专家-rank 映射** 先算出来，并且让所有 GPU 达成一致，随后把 **该算表** 交给后台权重加载守护进程。”

    1. 先让本 Rank 计算「新路由表」

    • 真正干活的是 ModelRunner (tp_worker / draft_worker 内部)其核心代码片段↓

    • rebalance_experts() 调用eplb的rebalance组件返回重排后物理专家到逻辑专家的映射

    • 结果写入 **tmp_** 张量，此时主模型仍用 old 表。

    2. 用 三态码 同步所有 Expert-Parallel Rank 的结果

    码值 含义
    1 本 rank 计算成功
    −2 本 rank 失败，可回退
    −1 致命失败，必须整机重启

    • 只要任何 rank 上报 −1 → 立即 raise Exception 让监控重启服务。

    • 若出现 −2（非致命），只有 EP 0 会调用self.rearrange_experts_failed() 写标志并放弃本轮重排。

    3. 全部 OK 后，唤醒后台 loading_model_weights_thread

    • infos 包含

      • 新旧model_ep_rank_to_expert_id_list 表格

      • 模型路径 / load_format / revision …

    • 子进程拿到后开始 磁盘→/dev/shm 的权重搬运。

    4. 本函数之后发生的事

    • need_caculate_expert_rank_table 置 False，防止重复触发。

    • Scheduler 的事件环会继续运行，直到下一轮 all_gather 看到REARRANGE_EXPERT_MAGIC_NUM，才进入真正的 execute_rearrange_experts()—— 也就是把刚才搬好的新权重切换进 GPU 模型。

    小结 — 时序图

    execute_caculate_expert_rank_table() 到此结束，真正的权重加载和后续

    execute_rearrange_experts() 将在下一阶段完成。

    4 . 后台 I/O：磁盘 → /dev/shm (loading_model_weights_thread)

    主循环 —— “收件 → 读盘 → 写 shm → 回执”

    线程一直阻塞在 mg_conn.recv()。一旦收到了调度器发来的任务（数据结构其实是一个列表，里面的元素形如 (model_name, AsyncEPLoader)），就开始下面的步骤：

    1. 遍历每个模型（main、mtp 等）

      • 从 AsyncEPLoader 拿到 ep_rank。

      • 调 load_experts_weight_from_disk() 把需要换的 expert 权重从磁盘读进 CPU tensor，并存到 info.cached_weights。

        1. 确定本 rank 要管哪几个 expert

          • expert_per_rank 决定“一张卡托几个 expert”。

          • start_idx / end_idx 从全局专家表里切出属于当前 ep_rank 的那一段。

        2. 比对旧表 VS 新表遍历所有层：

          • old_expert_ids_all：本 rank 在旧模型里托管的 expert id 列表。

          • new_expert_ids_all：新模型想让本 rank 托管的 id 列表。

          • 把两张表一行行、一列列对比——只要发现 “旧 id 不存在” 或 “旧 id ≠ 新 id”，就把 (layer_id, new_expert_id) 记进 need_to_reload。这说明这块权重必须重新加载。

        3. 真正去读盘（可能读 0 个，也可能很多个）

          • 如果 need_to_reload 为空，直接成功返回。

          • 否则调用 self.load_expert_weight_from_disk(need_to_reload)

            • 这个子函数会用 vLLM 的 loader 把对应权重文件读成 CPU tensor，放进 self.cached_weights。

        4. 返回值

          • 成功：True, "succeed"

          • 失败：False, errmsg（任何异常都会记录详细 traceback，然后失败返回）

        此时权重还只是留在 Python 进程的 CPU 内存，并没有写到共享内存，也没有上 GPU。

      • 如果读取成功，统计一下本模型本 rank 读进来的总字节数，只用于打印；然后调用save_tensor_to_shm_mem把这些 tensor 写入 /dev/shm/{name}_rank_{ep_rank}_ep_dyn.weights。写入时同时生成一份索引：每个 tensor 的名字、在文件中的偏移、大小、shape、dtype；这些索引稍后要带回给主线程。

        • 文件准备

          • /dev/shm/{name}_rank_{ep_rank}_ep_dyn.weights 在主线程里早就 truncate 好了，大小由环境变量或模型尺寸决定。

        • 顺序写入 + 建索引

          • tensor_infos 就是这块共享文件的“目录索引”：哪个 tensor、写在文件的哪儿、多大、shape、dtype。

          • 如果写超文件大小会抛 IOError——防止配置的 /dev/shm 容量不够。

        • 日志与返回

          • 打印“这次总共写了多少 GB”，然后把 tensor_infos 返回给调用方。之后外层线程会把 (model_name, tensor_infos) 回传给 GPU 侧的 async_update_weight_thread。

      • 如果读取失败，就记日志并把 result 标为 False。

    2. 异常兜底

      • 整个 for 循环包在 try/except 里。发生未捕获异常时，会把 weight_infos 清空并把 result 置 False，保证不会把残缺数据传回去。

    3. 回传结果

      • 构造 request_data：用 data_conn.send(request_data) 送回给调度器里负责 GPU-侧覆写的 async_update_weight_thread。

        发送完就回到 while True 头部，等待下一次 mg_conn.recv()。

    设计要点和背后的目的

    • 把 I/O 独立出来读磁盘、压缩解码等都是纯 CPU 操作；放在这个线程里做，不会阻塞主调度循环。

    • 零拷贝切换线程把 tensor 原样写进 /dev/shm 的映射文件。调度器主线程拿到 offset 之后可以直接 torch.frombuffer 构造 tensor，再把 cudaHostRegister 过的页映射到 GPU，省掉一次 CPU→GPU 的 memcpy。

    • 最小通信量线程和主进程之间只传“小索引表”，不传大块数据。因此 Pipe 或 ZMQ 只需要几 KB，而几 GB 的权重已经提前落在共享内存。

    • 统一错误上报result=False 表示本 rank 加载失败；主进程会和其他 rank 的结果做 all_gather 再决定是整体回滚还是继续。

    整个过程保证了 读取-写共享内存-GPU 覆写 的流水线化，一次热更新对前端推理服务的阻塞时间大幅缩短。

    5 . CPU 覆盖：/dev/shm → CPU (async_update_weight_thread)

    • 用 load_tensor_from_shm_mem() 对 /dev/shm 里的那段内存构造 CPU Tensor。这里调用 torch.frombuffer(...)，不做任何复制；Tensor 的 storage 直接指向那块 pinned host memory。

    • 把 (tensor_name, tensor) 列表交给 update_weights_to_model_runner(), model_runner仅做self.cached_weights = weight。此时权重还停留在 CPU（准确地说，在共享内存那块页锁定内存里）。

    • 线程随后用 HTTP /register_rearrange_result 告知 EP 0 自己权重已加载到cpu

    6 . ep-rank 0 收到其它 rank 的 register_rearrange_result 之后会做的事

    • HTTP 入口

      每个 rank 在 async_update_weight_thread 里调用sync_load_result_to_rank0(rank0_ip, rank0_port, ep_rank, success, message)

      这会对 rank 0 上运行的 Flask/FastAPI 路由POST /register_rearrange_result 发送 JSON { user, passwd, ep_rank, success, message }：

    • 写结果文件（不阻塞主线程）

      • 这个路由直接调用RedundantAsyncLoadResult.register_rearrange_result()内部逻辑只是把内容落到REDUNDANT_ASYNC_LOAD_META_DIR/tmp_redundant_async_results/下的一份 JSON 文件里，文件名形如rank_<ep_rank>_async_load_result.json。整个操作很短暂（几十毫秒），不会触碰 GPU，也不依赖torch.distributed，对 Scheduler 的主循环来说几乎无感。

    • rank 0 如何“等齐”

      rank 0 自己的 async_update_weight_thread 会定时调用self.async_load_result.is_all_success() 轮询那个目录, 检查文件数量是否等于rank_num。

      • 还没收齐：返回 (all_succ, wait_register, fatal_error) = (False, True, False)，线程什么也不做；Scheduler 继续正常排队、forward、采样，服务用户请求。

      • 全部收齐且都成功：

        • 线程把 self.need_rearrange_experts 设成 True

        • 把 self.rearrange_experts_check_failed 设成 False

      • 任意 rank 失败：

        • 线程把 self.rearrange_experts_check_failed 设成 True。

    6 . 第二次魔数 → 真正重排

    再次 all-gather 遇到 REARRANGE_EXPERT_MAGIC_NUM → Scheduler 调 execute_rearrange_experts()→ tp_worker.rearrange_experts()→ ModelRunner.rearrange_experts()→ModelRunner.do_rearrange_experts()：

    1. 更新路由表: redundant_table_manger.update_expert_rank_table()

    2. 加载新专家权重: update_experts_weight_from_disk(new_rank_expert_list, ep_rank)→load_expert_weight_from_disk(need_to_reload)

      • 读取顺序：

        • 若 self.cached_weights 已有对应张量 → 直接用它（避免再拉磁盘）；

        • 否则调用 vLLM DefaultModelLoader 再读一次磁盘。

      • model.load_weights(weights_list, copy_expert_weight=True)只覆盖需要变动的 Expert 子模块，并把它们移进 GPU。

    3. All-gather 检查是否有 rank 失败

      • -1：普通失败 → 回滚

      • -10：致命失败 → 抛异常，需整机重启

    4. 若前面失败且已复制权重，调用rollback_experts_weight_from_disk() 把旧专家重量回灌回来。

    5. cached_weights 清零，result.dump() 记录 json。

    8 . Scheduler 状态复位

    成功走完后：

    并继续正常推理，已使用 新专家+新路由表。

    9 . 整体时序图

    10 . 关键点回顾

    • 双存储层：磁盘 → /dev/shm(pinned) → GPU；显存峰值可控，I/O 与推理并行。

    • 两阶段同步：魔数 + all_gather 保证 所有 rank 同步进/退。

    • ModelRunner 最终执行：

      • 持有 redundant_table_manger，真正交换路由表；

      • 利用 cached_weights 避免重复 I/O；

      • 失败即回滚，致命失败抛异常，由外层监控重启。

    至此，结合 Scheduler 与 ModelRunner，整条「在线专家重排」链路闭环。

    QA

    1. 为何不直接“一条线程读盘→CPU”, 要分loading_model_weights_thread和async_update_weight_thread？

      GPU side 线程和 I/O 线程不在同一进程空间；用管道传几 GB 的 tensor 不现实，/dev/shm 可被两边 mmap，天然是最快的共享媒介。

    2. 为什么loading_model_weights_thread是process, async_update_weight_thread是thread,

      核心思路：

      搬磁盘 → /Dev/Shm 属于“纯 CPU + 大量 I/O”——放到单独 Process；

      把 /Dev/Shm 的页映射成 Tensor、再写进 GPU 模型属于“GPU-内部的轻量操作”——留在主进程用 Thread。

      loading_model_weights_thread 为什么用 Process

      1. 彻底隔离 Python GIL 与 GPU Runtime: I/O 进程只做磁盘读写和文件 mmap，不需要任何 CUDA 句柄。放到独立 Process 完全绕过 GIL，也避免了“子进程 fork 后访问 CUDA context 会崩”的风险。

      2. 可随意申请、释放巨大临时 DRAM: 进程结束时内核直接回收虚拟内存，不会把几十 GB 的页留在主推理进程的 RSS 里；即使中途崩溃也不会污染 GPU 侧的状态。

      3. 专职 CPU-bound 任务，不打断推理: 读盘、解压、quantize 都是重 CPU 的；单独进程占满核不影响主进程调度 forward。

      4. 需要创建和 mmap 固定大小的 **/dev/shm/..._ep_dyn.weights**: 这一步必须 os.ftruncate + mmap + cudaHostRegister，对每个 rank 写同一文件。让一个纯 CPU 进程集中做，比在持有活跃 CUDA context 的进程里做更可靠。

      async_update_weight_thread 为什么用 Thread

      1. 必须直接调用模型对象的方法: 它要执行 model_runner.update_weights_to_model_runner()和最终的 model.load_weights()，这些对象都只存在于主进程地址空间，如果用 fork 出来的子进程，会拿不到原始 Python 对象，也无法共享 CUDA handle。

      2. 需要复用主进程的 CUDA context: 调用 torch.frombuffer(...).cuda() 或 tensor.to(device) 时会触发 H2D，只有和 Scheduler/TpWorker 同一进程的线程才能安全复用当前 GPU 流和显存池。

      3. 工作量很小，不值得再开进程: thread 只是把索引表转成 Tensor view，再调用一次 model.load_weights()，整个过程在毫秒级；用线程就能利用现成锁与条件变量、无需跨进程通信。

      4. 需要持续轮询结果文件并设置内部标志位: 它会修改 self.need_rearrange_experts 等 Scheduler 字段，Thread 直接写共享内存即可，Process 则需要 Pipe／Queue，再加同步逻辑。

    3. GIL在磁盘读写方面会造成什么问题

      在 CPython 里，任何执行 Python 字节码 的线程都要先拿到 GIL（Global Interpreter Lock）。读写磁盘这类 I/O 看似“阻塞系统调用会自动释放 GIL”，但实际上仍会出现下面几类掣肘，导致 重 I/O 线程和推理主线程无法真正并行。

      1. 读写循环仍不断抢 GIL

      读大文件通常是“读一块 → Python 逻辑 → 读下一块”，只要有 Python 层数据处理（解压、checksum、路径拼接、列表 append …），每次都重新占用 GIL。

      结果：即使 read(2) 本身会在内核态阻塞，线程 A 还是会频繁把 GIL 锁住，线程 B（负责推理调度）就只能等，下行延迟跟着抖。

      2. 内存拷贝/解析是 CPU-bound，不会释放 GIL

      • ctypes.string_at(ptr, size)

      • pickle.loads(...) / torch.load 里的反序列化

      • Python 循环拼 tensor name、统计大小……

      这部分属于纯 Python 计算；一旦开始就独占 GIL，其他线程全部停摆。重排时要搬几百 MB～数 GB 参数，这段 CPU 拷贝足以让推理线程卡顿百毫秒甚至秒级。

      3. 垃圾回收、内存管理也受 GIL 保护

      读完权重后会建很多临时 bytes / Tensor，再被 GC 回收。GC 的追踪和 PyMem_Free 都要持有 GIL，容易与实时推理线程“打架”。

      为什么 换进程 就能规避

      • 进程间没有共享 GIL，I/O 进程即使 100 % 占用 CPU，也不会阻塞主进程的 Python 解释器。

      • mmap + cudaHostRegister 只在 I/O 进程里做一次；主进程后续 torch.frombuffer 不再触碰 Python 级 I/O。

      • 出错可直接杀 I/O 进程，主推理服务无感知，可靠性更高。

      • 释放内存更干净——I/O 进程退出，内核把巨大的 RSS 一次性回收，不污染主服务的 heap。

      因此，在 SGLang 的重排链路里 loading_model_weights_thread 被设计成独立 Process，确保磁盘→/dev/shm 的“重 I/O + 重 CPU”阶段与持 GIL 的推理主循环彻底解耦，即使偶尔抢到 GIL 也不会对在线延迟造成可感知影响。
