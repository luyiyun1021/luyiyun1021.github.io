组件集成架构

DataParallelController

从DataParallelController开始，终于到了管理多 GPU 的控制器。目前为止，我们梳理过：

ModelRunner->TpModelWorker->Scheduler

到这里，所有的文章都是集中在单卡上的 TP 做的，为什么突然就到了 DP 多卡呢？直观上，显然 DP 相比 TP 是更上一层，为什么 SGLang 没有TensorParallelController，而直接到了DataParallelController？

事实上，SGLang 的DataParallelController同时也进行了 TP 和 DP 的统一管理。TP 需要管理的内容不多，大家都是一致的，做好broadcast input和allreduce activations即可。所以，DataParallelController将 TP 的管理和更上层的 DP 管理统一到了这一层，换言之，这是个多级并行控制器。

源码地址：sglang/sglang/srt/managers/data_parallel_controller.py

  1. 多级并行架构管理
  • 管理数据并行(DP)和张量并行(TP)的多级结构
  • 为每个 DP 组分配独立的 GPU 资源块
  • 支持多节点分布式部署
  1. 负载均衡
  • 实现多种负载均衡策略
  • 在 DP workers 间分发请求
  • 动态调整工作负载
  1. 进程间通信
  • 使用 ZMQ 管理复杂的进程间通信
  • 处理 tokenizer 到 worker 的请求转发
  • 支持控制消息的广播
  1. 请求调度
  • 接收和分发推理请求
  • 处理特殊控制消息
  • 维护请求的生命周期

流程梳理

  1. 服务端启动, 若dp_size = 1, 则为每个tp_rank初始化一个scheduler进程, 若dp_size > 1, 通过run_data_parallel_controller_process初始化一个DataParallelController, 调用launch_worker_func->launch_tensor_parallel_group->run_scheduler_process按照dp_group->tp_group的层级为每个 dp_rank 的每个 tp_rank 创建一个 Scheduler 进程(一个 Scheduler 对应一张卡), 并把发给每个 tp_group 的 Scheduler 的 zmq socket (一个根据dp_rank命名的临时文件, 用于进程间通信) 存在self.workers列表中 (每个 tp group / dp_rank 的所有 Scheduler 的 ipc endpoint是相同的, 因此dp_controller向一个worker发送请求, 这个tp_group下的所有Scheduler都会收到请求), Scheduler和DataParallelController分别调用event_loop()开启无限事件循环
  2. DataParallelController的event_loop()接收到来自Tokenizer发来的TokenizedGenerateReqInput请求, 调用dispatching方法, 例如round_robin_scheduler用round_robin算法或者dp_affinity_scheduler根据外部指定的 dp_rank, 向相应worker发送请求, 如果是接收到其他的控制请求,比如专家重排等, 会向所有worker发送请求
  3. Scheduler 通过 recv_requests 接收请求，取出当前所有已经在zmq中的请求, 如果tp_size != 0, 只有tp_rank = 0的node会处理请求, 并把收到的请求broadcast到整个tp_group . 随后调用 process_input_requests 处理输入，通过 handle_generate_request 管理生成请求Req的逻辑，并将其加入 waiting_queue。
  4. 从 waiting_queue 中，Scheduler 使用 get_next_batch_to_run 获得 prefill batch, 为即将处理的请求创建 ScheduleBatch。
  5. Scheduler 调用prepare_dp_attn_batch, 对所有的 ep_rank 的 local batch 的 token 数量进行 all_gather 操作, 获得 global_num_tokens, 这里做了所有rank的同步是为了防止在专家重排阶段有rank单独进入run_batch阶段
  6. Scheduler 执行 run_batch 函数，将 ScheduleBatch 转换为 ModelWorkerBatch。
    • Scheduler 调用 TpModelWorker 的 forward_batch_generation，等待 logits_output 和 next_token_ids。
  7. Scheduler 通过 process_batch_result 处理批次结果，通过 check_finished 验证完成状态, 转发到 Scheduler 的 stream_output。
  8. 在 stream_output 函数中，Scheduler 处理输出，将其包装成 BatchTokenIDOut，并发送给 DetokenizerManager。
  9. DetokenizerManager 在其事件循环中接收 BatchTokenIDOut，处理后生成 BatchStrOut并返回给 TokenizerManager。
  10. TokenizerManager 在其事件循环中接收结果，通过 handle_loop 处理并更新内部状态，然后将响应返回给Server 。

各rank同步点

  1. prepare_dp_attn_batch中的all_gather
  2. DPEPMoE中的 all_to_allDispatch (MoE模型下)
  3. DPEPMoE中的 all_to_allCombine (MoE模型下)
