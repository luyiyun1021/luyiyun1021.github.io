Sglang Deepseek模型 Prefill阶段流程梳理

发表于 2025-06-12 分类于 大模型 ， 推理技术 ， Sglang 阅读次数： 本文字数： 1.6k 阅读时长 ≈ 6 分钟

  1. 用户启动 Server ，初始化 FastAPI App、TokenizerManager、DetokenizerManager 和 Scheduler，每个组件运行各自的无限事件循环（infinite event loop）。
  2. 用户向 FastAPI Server 发送 /v1/chat/completions 请求，其中max_tokens = 1, Server 通过 v1_chat_completions endpoint 将请求转发到 TokenizerManager。
  3. v1_chat_completions 函数将请求转换为 ChatCompletionRequest，再通过v1_chat_generate_request转换为 GenerateReqInput，并调用 TokenizerManager 的 generate_request 方法。
  4. TokenizerManager 调用_tokenize_one_request对请求进行 tokenization，转化为TokenizedGenerateReqInput并以 Python 对象（pyobj）形式将其通过_send_one_request转发给 Scheduler (通过zmq ipc socket)，同时调用 TokenizerManager 的 _wait_one_response 方法。
  5. Scheduler 在事件循环 event_loop_normal 中处理请求：
  • Scheduler 通过 recv_requests 接收请求，调用 process_input_requests 处理输入，通过 handle_generate_request 管理生成请求Req的逻辑，并将其加入 waiting_queue。
    • 从 waiting_queue 中，Scheduler 使用 get_next_batch_to_run 获得 prefill batch, 为即将处理的请求创建 ScheduleBatch。
    • Scheduler 执行 run_batch 函数，将 ScheduleBatch 转换为 ModelWorkerBatch。
      • Scheduler 调用 TpModelWorker 的 forward_batch_generation，等待 logits_output 和 next_token_ids。
        • 调用 self.attn_backend.init_forward_metadata(forward_batch)
          • 调用 FlashInferMLAIndicesUpdaterPrefill, 根据req_pool_indices, 对于attention backend中的req_pool->token_to_kv_pool进行维护和更新
        • 调用 self.model.forward(forward_batch.input_ids, forward_batch.positions, forward_batch)进行模型前向
          • 进入到model的DeepseekV2ForCausalLM->DeepseekV2Model->DeepseekV2DecoderLayer, 进行(DeepseekV2AttentionMLAMOE + DeepseekV2MoE)模块layer次数的迭代
          • DeepseekV2AttentionMLAMOE
            • DeepseekV2AttentionMLA: 调用 forward_normal 函数
              • 根据当前输入的hidden state算出latent_cache, 调用token_to_kv_pool的set_kv_buffer函数, 把latent_cache存在out_cache_loc预先分配的位置
              • 调用self.attn_mqa即FlashInferAttnBackend的forward函数
            • 调用shared_experts前向, 过gate_up_proj, act_quant_fn, down_proj得到shared_output
            • 过MoEGate得到router_logits, 对于每个专家的原始打分
            • 调用select_experts使用分组topk算法获得topk_weights, topk_ids
              • 参数说明:
                • hidden_states: 输入的隐藏状态，形状为 (batch_size, hidden_dim);
                • gating_output: 路由器的输出，表示每个输入对每个专家的偏好，形状为 (batch_size, num_experts);
                • correction_bias: 用于修正的偏置项，形状为 (num_experts,);
                • topk: 每个输入选择的专家数量, config中的num_experts_per_tok, 为8;
                • renormalize: 是否对选择的专家权重进行重新归一化;
                • num_expert_group: 专家的分组数量, 对应config中的n_group, 为8;
                • topk_group: 每个分组中选择的专家数量, config中的topk_group, 为4。
              • 逻辑: 将专家分组，每组包含(config.n_routed_experts + global_server_args_dict["re_ep_size"])/ num_expert_group = (256个普通专家 + 32个冗余专家) / 8 = 36个专家, ep=32的话, 每张卡9个专家(8个普通专家 + 1个冗余专家), 那么一个专家组包含四张卡。对每个分组内的专家得分(由gating_output sigmoid得到)进行 top-2 操作，并将 top-2 的得分相加，得到每个分组的总得分。从每个分组中选择得分最高的 topk_group=4 个分组。在被选中的分组中的专家中选择得分最高的 topk=8 个专家。
            • 返回(output, residual, shared_output, None, None, None, topk_weights, topk_ids)
          • DeepseekV2MoE
            • 根据选出的专家, 过self.experts, 类型为DPEPMoE
              • 对输入x进行每token分组量化（speedgate.per_token_group_quant_fp8），得到量化后的hidden_states_fp8, 形状为 (num_tokens, hidden_size) 和 hidden_states_scale, 形状为 (num_tokens, hidden_size // 128)，组成x_e4m3元组
              • 使用self.ep_group.deep_ep_buffer.get_dispatch_layout方法获取调度布局信息
              • 使用self.ep_group.deep_ep_buffer.dispatch方法进行all_2_all调度，将输入x根据topk_idx和topk_weights分配到不同的专家, 返回recv_x, recv_topk_idx, recv_topk_weights
              • 调用_prefill_local_expert_forward_fp8方法进行本地专家的前向传播计算。输入为 recv_x[0](hidden states) 形状为 (num_tokens, hidden_size), recv_x[1] (hidden_states_scale) 形状为 (num_tokens, hidden_size // 128), recv_topk_idx, 形状为 (num_tokens, topk) , recv_topk_weights, 形状为 (num_tokens, topk), recv_num_tokens_per_expert_list, 每个本地专家的收到的token数, 形状为 (self.num_experts_per_partition)
                • 预处理:

                  • 把每个专家实际 token 数向上取整到128的倍数, 得到取整后的num_all_tokens, 这些token是有可能有重复的, 比如说专家1收到token1,2, 专家2收到token1,3, num_all_tokens是256

                  • 构造recv_x_all_fp8, 含义为每个token(包括padding的token)的hidden, 形状为(num_all_tokens, hidden_size), 通过m_indices决定这个token被发送到哪个专家

                  • recv_x_all_scale, 形状为 (num_all_tokens, hidden_size // 128)

                  • m_indices, 含义为每个token(包括padding的token)发送到哪个专家, 形状为(num_all_tokens),值为专家id

                    • 假设有 3 个专家，实际 token 数 N = [155, 9, 3]
                      • 取整后 N_128: [256, 128, 128]
                      • 展开序列 m_indices（前 20 行）: [0,0,…(256×),1,1,…(128×),2,2,…(128×)]
                      • 行 0-255 属于 expert 0，256-383 属于 expert 1，依此类推。

                  • token_to_m, 每个不重复的token对应recv_x_all_fp8中的哪些行数, 形状为(num_tokens, topk),

                  • token_counts, 每个不重复的token关联了几个专家, 形状为(num_tokens),

                  • token_weights, 每个token对应的topk_weight, 形状为(num_all_tokens)

                    • GroupGemm-0:

                      """
Perform a grouped GEMM (contiguous format) with FP8 inputs and BF16 output, with 1x128 LHS scaling and 128x128 RHS scaling.

Requirements:
    LHS, RHS, RHS scaling factors, and output tensors must be in contiguous format.
    RHS and RHS scaling factors are required to be transposed.
    The LHS scaling tensor requires a TMA-aligned transposed format, if your input does not match the requirement,
    this function will do a transposing with a set of slow PyTorch operations.
    On the M axis, inputs are grouped into several batches, of which batch sizes aligned to `get_m_alignment_for_contiguous_layout()` (128).

Arguments:
    lhs: the first element is an FP8 tensor (typed `torch.float8_e4m3fn`) of shape `[m_sum, k]`,
    the second element is an FP32 1x128 scaling tensor for LHS of shape `[m_sum, ⌈k / 128⌉]`.
    rhs: the first element is an FP8 tensor (typed `torch.float8_e4m3fn`) of shape `[num_groups, n, k]`,
    the second element is an FP32 128x128 scaling tensor for RHS of shape `[num_groups, ⌈n / 128⌉, ⌈k / 128⌉]`.
    out: the BF16 output tensor of shape `[m_sum, n]`, representing the result.
    m_indices: a tensor of shape `[m_sum]` with type `torch.int`.
    `m_indices[i]` records the group which the i-th row of the LHS belongs to,
    which means that the i-th row of the LHS matrix will be multiplied with `rhs[m_indices[i]]`.
    Values of `m_indices` in every-m-alignment-block must also be the same.
"""
                      • 调用deep_gemm.m_grouped_gemm_fp8_fp8_bf16_nt_contiguous, 输入是(recv_x_all_fp8, recv_x_all_scale), (self.w13_weight, self.w13_weight_scale_inv), gateup_output, m_indices, 输出是 bf16 gateup_output，形状为(num_all_tokens, self.w13_weight.shape[1])
                • SiLU:
                  • down_input = F.silu(gateup_output[…, :d]) * gateup_output[…, d:], d = gateup_output.shape[-1] // 2
                • 量化 到 FP8
                  • speedgate.per_token_group_quant_fp8(down_input, down_input_fp8, down_input_scale, group_size=128, epsilon=1e-10, dtype=float8_e4m3fn, row_major=True), 行分组量化（128 元素一组）+ 每组 scale，兼容下一步 GroupGEMM-1。
                • GroupGemm-1:
                  • 调用deep_gemm.m_grouped_gemm_fp8_fp8_bf16_nt_contiguous, 输入是(down_input_fp8, down_input_scale), (self.w2_weight, self.w2_weight_scale_inv), down_output, m_indices, 输出是 bf16 down_output，形状为(num_all_tokens, self.w2_weight.shape[1])
                • Combine-Convert — 把重复的token序列重新聚合成不重复的token 序列:
                  • 输出x_to_combine, 根据token_to_m, 把down_output * token_weights的结构填入, 形状为(num_tokens, hidden_size)
              • 使用self.ep_group.deep_ep_buffer.combine方法进行all_2_all合并，将不同专家的输出合并回原始的张量
              • 将合并后的输出combined_x乘以routed_scaling_factor，并加上shared_output，得到最终的输出x，并返回。
    • Scheduler 通过 process_batch_result 处理批次结果，通过 check_finished 验证完成状态。由于max_tokens = 1, 请求被判断为完成，转发到 Scheduler 的 stream_output。
    • 在 stream_output 函数中，Scheduler 处理输出，将其包装成 BatchTokenIDOut，并发送给 DetokenizerManager。
  1. DetokenizerManager 在其事件循环中接收 BatchTokenIDOut，处理后生成 BatchStrOut 并返回给 TokenizerManager。
  2. TokenizerManager 在其事件循环中接收结果，通过 handle_loop 处理并更新内部状态，然后将响应返回给Server 。
