Sglang Scheduler端逻辑梳理

假设prefill节点部署在10.63.69.12:8001
decode节点部署在10.63.64.98:8001

总体流程:
prefill节点:
curl -s http://10.63.69.12:8001/v1/chat/completions -d “{"model": "DeepSeek-R1", "temperature": 0, "messages": [{"role": "user", "content": "The president of the United States is "}], "max_tokens": 1, "temperature": 0, "kv_transfer_params":{"mooncake_kv_transfer_param": {"remote_ip":"10.63.64.98","remote_dp_local_rank":0,"id":"id-1"},"global_dp_rank":0, "remote_global_dp_rank": 1}}”

  1. 发送max_tokens = 1的请求, 附带 decode node ip, request 的唯一id, remote_dp_local_rank, global_dp_rank, remote_global_dp_rank(后面这些用来算端口)
  2. Scheduler 在事件循环 event_loop_normal 中处理请求：
  • Scheduler 通过 recv_requests 接收请求，调用 process_input_requests 处理输入，通过 handle_generate_request 管理生成请求Req的逻辑，并将其加入 waiting_queue。
    • 从 waiting_queue 中，Scheduler 使用 get_next_batch_to_run 获得 prefill batch, 为即将处理的请求创建 ScheduleBatch。
    • Scheduler 执行 run_batch 函数，将 ScheduleBatch 转换为 ModelWorkerBatch。
      • Scheduler 调用 TpModelWorker 的 forward_batch_generation，等待 logits_output 和 next_token_ids。
      • 把这个batch添加到 send_cache_queue 中, submit_task 提交一个 send_kv_cache 任务, send_kv_cache 传入这个batch kvcache的地址, input_ids的长度等, 用self.trans_agent.send_kv_caches把kvcache 传到 MooncakeKVTransferParam 的 remote ip
    • Scheduler 通过 process_batch_result 处理批次结果，通过 check_finished 验证完成状态。由于max_tokens = 1, 请求被判断为完成，转发到 Scheduler 的 stream_output
    • 在 stream_output 函数中，Scheduler 处理输出，将其包装成 BatchTokenIDOut，并发送给 DetokenizerManager。
  1. DetokenizerManager 在其事件循环中接收 BatchTokenIDOut，处理后生成 BatchStrOut (其中额外添加output_ids, 即生成的token id) 并返回给 TokenizerManager。
  2. TokenizerManager 在其事件循环中接收结果，通过 handle_loop 处理并更新内部状态，然后将响应返回给Server 。

deocde节点:
请求中额外添加prefill node返回的 output_ids, remote ip设为prefill节点

  1. 发送正常的请求, 额外添加prefill node返回的 output_ids, prefill node ip, 和 prefill request 相同的 id, remote_dp_local_rank, global_dp_rank, remote_global_dp_rank(后面这些用来算端口)
  2. Scheduler 在事件循环 event_loop_normal 中处理请求：
  • Scheduler 通过 recv_requests 接收请求，调用 process_input_requests 处理输入，通过 handle_generate_request 管理生成请求Req的逻辑，并将其加入 waiting_queue。将req的首个生成的 token 设置为 req.first_token_ids = recv_req.kv_transfer_params.output_ids[0], 即用 kv_transfer_params 中的 output_ids[0] 作为本次解码阶段的初始 token
    • 从 waiting_queue 中，Scheduler 使用 get_next_batch_to_run 获得一个 prefill batch 为即将处理的请求创建 ScheduleBatch。
      • get_new_batch_prefill 的逻辑
      • 等待队列为空，则直接返回读 Cache 已就绪的批次（get_read_cache_done_batch()）。
      • 等待队列不为空, 从waiting_queue拿出一个Prefill request, 生成一个新批次后
        • 如果这个req output_ids为空, 即还没有生成过decoding token, 把first_token_ids添加到output_ids,
        • 把这个batch添加到reading_cache_queue中, submit_task提交一个load_cache任务, load_cache传入这个batch kvcache的地址, 用self.trans_agent.recv_kv_caches把kvcache读进来, 读取哪个是通过MooncakeKVTransferParam中的id即req的标识, load完后设置new_batch.loaded_cache = True
        • 随后调用get_read_cache_done_batch, 遍历 reading_cache_queue, 检查哪些批次的 loaded_cache 属性已就绪, 使用 all_gather 收集所有 TP rank 的 ready 信息, 找到所有rank都完成 (all_ones) 的第一个批次索引 all_one_index, 如果找到一个批次在所有TP rank都就绪, 则将它从 reading_cache_queue 中移除并作为 loaded_batch 返回, 如果没有返回 None
    • Scheduler 执行 run_batch 函数，将 ScheduleBatch 转换为 ModelWorkerBatch。
      • Scheduler 调用 TpModelWorker 的 forward_batch_generation，等待 logits_output 和 next_token_ids。
    • Scheduler 通过 process_batch_result 处理批次结果，使用 tree_cache.cache_finished_req(req) 缓存请求，并通过 check_finished 验证完成状态。对于未完成的请求，Scheduler 继续其事件循环，直到这个请求满足结束条件；对于已完成的请求，则转发到 Scheduler 的 stream_output。
    • 在 stream_output 函数中，Scheduler 处理输出，将其包装成 BatchTokenIDOut，并发送给 DetokenizerManager。
  1. DetokenizerManager 在其事件循环中接收 BatchTokenIDOut，处理后生成 BatchStrOut 并返回给 TokenizerManager。
  2. TokenizerManager 在其事件循环中接收结果，通过 handle_loop 处理并更新内部状态，然后将响应返回给Server 。

Q:

  • decode过程中, kv cache被换出怎么办, 由于之前已经消费完了, pipe里面已经没有对应的kv cache了, load cache不会ready
    • 当前做法: 直接在retract过后把request直接drop掉, 在上游再重新进行一次完整推理实现failover, 正常应该是放回waiting queue里等待下次调度,

底层 kv cache transfer agent 逻辑梳理

Mooncake Pipe

Sender 端流程（send_kv_caches）

  1. 数据准备与打包
    • 在调用 send_kv_caches(tensor, loc, transfer_param) 时，发送端会遍历每一层（layer）：
      • 从每一层的 KV 缓存 tensor 中，根据索引 loc 提取需要发送的行（代表 token 对应的kvcache）。
      • 将各层提取出的数据按层堆叠，形成一个形状为 (layer_count, num_tokens, 1, d) 的大 tensor（即 send_tensor）。
    • 同时，根据传输参数中的 id 和总层数(61)生成一个唯一的缓存键（cache_key），并利用MooncakeKVTransferParam配置中的信息构造出远端地址（remote_addr）。
  2. 调用底层 Engine 发送数据
    • 发送端将打包好的 tensor 交给管道对象（DynamicMooncakePipe）的 send_tensor 方法。
    • 该方法在内部调用 DynamicMooncakeTransferEngine.send_bytes：
      • 通过底层c++引擎mooncake_vllm_adaptor调用 allocateManagedBuffer(length) 为数据分配一个缓冲区，并用 writeBytesToBuffer 将序列化后的数据写入该缓冲区。
  3. 握手过程与连接确认
    • 在发送数据之前，为保证接收端已就绪，发送端通过其绑定的 ROUTER socket（send_socket）等待对方的握手消息。
    • 具体来说：
      • 接收端在建立连接后，会通过其 DEALER socket 发送一条特殊的 ping 消息。
      • 发送端后台有一个任务（由 recv_recv_sockets_ping 启动）不断调用 recv_multipart()，当接收到来自远端 DEALER 的 ping 消息后，会将该 DEALER 的身份（identity）存入字典 connected_recv_sockets。
      • 发送端在发送实际数据前，进入一个等待循环（while (not connected_recv_sockets.get(remote_id))），直到目标身份出现在 connected_recv_sockets 中。这确保了 sender 只有在确认远端已建立连接后才继续发送数据。
  4. 发送数据与确认
    • 握手确认后，发送端通过 send_socket 调用 send_multipart(...) 将数据消息发送出去。消息格式包含：
      • 第一帧：远端身份（remote_id），由 ROUTER 用于路由；
      • 后续帧：包含 cache_key、源缓冲区指针（src_ptr）和数据长度等信息（这些信息用于接收端重构 tensor）。
    • 发送端随后会异步提交一个任务 wait_for_ack，该任务调用 _get_sender_ack_socket 获取一个 DEALER socket（用于连接接收端的 ACK ROUTER），并阻塞等待 ACK 消息。当 ACK 收到后，调用底层 engine 的 freeManagedBuffer 释放发送缓冲区，完成整个发送流程。

Receiver 端流程（recv_kv_caches）

  1. 等待并建立连接
    • 接收端在调用 recv_kv_caches(tensor, loc, transfer_param) 时，首先根据传入参数构造 cache_key 和远端地址（remote_addr）。
    • 在底层管道的 recv_tensor(remote_addr) 中，会调用 DynamicMooncakeTransferEngine.recv_bytes。
    • 这里，接收端使用 DEALER 类型的 socket（由 _get_recv_socket 创建）主动调用 connect(remote_addr)（其中 remote_addr 是 sender 端绑定的地址，即 sender 的 ROUTER 端口, tcp://*:{self.local_port + 1}），并立即发送一条 ping 消息。这样，sender 端就能在其 recv_recv_sockets_ping 后台任务中捕获到对方的连接请求。
  2. 数据接收与解析
    • 接收端的 DEALER socket 调用 recv_multipart() 拉取由 sender 端发送的 multipart 消息。
    • 消息内容按照约定的协议进行组织：第一帧为 cache_key，第二帧为源缓冲区指针，第三帧为数据长度。
    • 接收端解析这些信息后，通过底层 engine 调用 allocateManagedBuffer(length) 为接收数据分配目标缓冲区，并调用 transferSync 将数据从发送端缓冲区复制到接收端缓冲区。随后使用 readBytesFromBuffer 读取出数据的字节流，再通过 pickle 反序列化为 tensor。
  3. 数据填充与缓存管理
    • 接收端得到的 tensor 形状为 (layer_count, num_tokens, 1, d)，正是发送端发送的 KV 缓存。
    • 接下来，recv_kv_caches 将接收到的 tensor 按层遍历，并将每一层的数据复制到本地缓存 tensor 的对应位置（tensor[i][loc].copy_(received_tensor[i])），完成缓存更新。
  4. 确认返回
    • 在数据接收和处理完毕后，接收端通过其 ACK ROUTER socket（receiver_ack，tcp://*:{self.local_port + 2}）发送一个ACK消息
    • 发送端的 wait_for_ack 任务在之前已通过其 ACK DEALER socket 阻塞等待此 ACK 消息。如果收到 ACK，则发送端释放其发送缓冲区并认为本次传输成功

缺点:

  • Mooncake Pipe 在数据传输过程中，会先将 KV 缓存从 GPU 移动到 CPU，再移动到内存缓冲区，多了一次复制操作
  • 需要手动管理内存缓冲区的分配和释放

Async Transfer Engine

初始化

  1. 初始化异步传输引擎DynamicMooncakeAsyncTransferEngine。

    1. 调用 self.initialize 方法初始化 mooncake 引擎，传入本地 URL、元数据服务器地址、协议、拓扑文件和元数据后端类型。

      • 创建传输引擎 engine_
      • 根据协议类型（rdma 或 tcp）安装传输层
      • 调用 allocateGlobalMemoryPool 函数分配全局内存池, 底层使用 cudaMallocHost 函数分配50GB的主机内存
      • 初始化任务计数器 task_counter_，将 running_ 标志设置为 true，并启动工作线程和传输工作线程。
        • workers 用于处理与缓存数据拷贝相关的任务，主要功能是将数据从 GPU 缓存拷贝到主机内存（DRAM）中, 并发设为20.
        • trans_workers 用于处理与数据传输相关的任务，主要功能是将数据从本地传输到远程节点, 并发设为1

    2. 初始化 ZeroMQ 上下文和套接字、线程池和任务队列

  2. 调用引擎的register_caches方法注册缓存, 传入Scheduler的token_to_kv_pool.kv_buffer。
    1. 按层遍历 kv_buffers 中的每个张量，调用 self.engine.registerCache 方法注册缓存
    2. 计算每个 token 所需的存储空间per_token_all_layer_size
    3. 创建一个可以容纳 5000 个包含所有 layer 的 token 的接收缓冲区Tensor, 调用 self.engine.registerRecvBuffer 方法注册接收缓冲区

Sender 端流程（send_kv_caches）

  1. 函数调用入口：在MooncakeKVTransferAgent类里调用send_kv_caches函数，传入参数transfer_param(包含对端的 ip, dp rank, 以及request id) 以及待发送的 request 的 kv cache 在 kv cache pool 中的索引loc和draft_loc。
  2. 调用引擎发送函数：调用self.engine.send_tensors函数，将张量索引loc、draft_loc，缓存键self._cache_key(transfer_param.id, self.layer_count)以及对端地址self._remote_addr(transfer_param)作为参数传入。
  3. send_tensors函数内部流程：
    • 数据准备：
      • 依据loc和draft_loc从self.caches和self.draft_caches中提取需要发送的数据，并进行克隆操作。
      • 计算数据的长度length。
    • 数据复制到 DRAM：
      • 调用self.engine.copyToDRAM函数，提交一个把数据从 GPU 复制到 DRAM的任务。worker 线程会从task_queue_ 中取出任务，调用allocateManagedBuffer从内存池分配task->size * task->layer_count * task->token_count大小的 buffer, 获得buffer_addr, 随后调用 doCopyToDRAM 方法执行实际的拷贝操作。doCopyToDRAM 方法使用 cudaMemcpyAsync 将数据从 GPU 缓存（cache_ptrs）异步拷贝到分配的 DRAM 缓冲区（buffer_addr）。拷贝完成后，通过 complete_task 方法将任务的处理结果（即 DRAM 缓冲区的地址）存储到 waiting_task_map_ 中，并通知等待的任务完成。
      • 调用self.engine.waitForTask函数，等待复制任务完成，获取 DRAM 中的缓冲区地址buffer_addr。
    • 记录等待确认信息：将缓冲区地址、数据长度和发送开始时间记录到self.waiting_ack字典里。
    • 获取发送套接字：调用self._get_send_socket函数，获取与对端通信的发送套接字。
    • 发送传输信息：把传输信息(cache_key, buffer_addr, length, self.nic_key, recv_deadline)打包后，通过发送套接字发送给对端。
    • 释放 buffer: 待接收到receiver端发送的对于cache_key的recv_ack, 调用self.engine.freeManagedBuffer释放该请求所申请的DRAM内存

Receiver 端流程（recv_kv_caches）

  1. 前期流程: receiver 端后台启动一个_recv_transfer_task, 接收sender端发送的传输信息, 从里面解析(remote_url, cache_key, src_ptr, r_length, r_device_name, recv_deadline)后把该等待传输的任务加入到waiting_trans队列中
  2. 函数调用入口：在MooncakeKVTransferAgent类中调用recv_kv_caches函数，传入参数transfer_param以及以及待接收的 request 的 kv cache 在 kv cache pool 中的索引loc和draft_loc。
  3. 调用引擎接收函数：调用self.engine.recv_tensors函数，将张量索引loc、draft_loc，缓存键self._cache_key(transfer_param.id, self.layer_count)以及对端地址self._remote_addr(transfer_param)作为参数传入。
  4. recv_tensors函数内部流程：
    • 记录等待接收信息：把张量索引loc和draft_loc记录到self.waiting_recv中。
    • 提交处理任务：提交一个_process_next_transfer任务到线程池，用于处理接收到的传输任务。
      • 获取传输任务: 从 self.waiting_trans 队列中获取一个传输任务，该任务包含对端 URL、缓存键、buffer 指针、数据长度、设备名称和接收截止时间。
      • 检查接收任务和传输任务是否匹配: 检查self.waiting_recv中是否存在与当前对端 URL 和缓存键对应的等待接收信息。
        • 如果存在，尝试从self.waiting_recv中弹出该信息。若弹出成功，将其解包为loc和draft_loc，并跳出循环。
        • 如果不存在，将该任务重新放入 self.waiting_trans 队列，并从队列中获取下一个任务。
      • 同步传输数据: 调用 self._transfer_sync 方法，同步地将数据从对端传输到本地缓存，传入对端 URL、源指针、缓存键、loc 和 draft_loc 作为参数。
        • 调用self.engine.addTransTask函数, 向 engine 提交一个从远端 buffer 接收 kv cache 并读取到 loc 的任务到trans_task_queue_中, 通过底层的传输引擎（如 RDMA 或 TCP）将数据从 sender 缓冲区传输到 receiver 端的在初始化时分配的接收缓冲区。传输完成后，调用 distribute_tensor_data 方法将接收到的数据分配到 receiver 端的 kv cache pool（caches_）中
      • 获取发送套接字：调用self._get_send_socket函数，获取与对端通信的发送recv_ack的套接字, 并发送包含cache_key的 ack
      • 传输完成通知: 调用self.engine.waitForTask函数，等待传输任务完成, 添加到trans_finished中
    • 等待传输完成：从self.trans_finished中阻塞并获取传输结果，若超时或者传输失败则抛出异常。
