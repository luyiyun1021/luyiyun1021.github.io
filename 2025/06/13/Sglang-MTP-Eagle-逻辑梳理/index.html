1. 初始化阶段（Server 启动）

# 触发点 关键字段 说明
1 Scheduler.__init__ self.spec_algorithm = SpeculativeAlgorithm.from_string(server_args.speculative_algorithm) 解析 CLI 参数 --speculative_algorithm。Eagle ⇒ SpecAlgorithm.EAGLE。
2 同处 if self.spec_algorithm.is_eagle(): EagleWorker 构造（见表-A）。同时：
① 申请独立 draft-KV buffer
② 建立 draft_policy（Queue 内优先级仅管 draft 请求）
3 self.decode_mem_cache_buf_multiplier = server_args.speculative_num_draft_tokens 估算 decode 所需额外 KV buf 空间（默认 2）。

表-A EAGLEWorker 构造

EAGLEWorker 内部再启动一个 ModelRunner（share 权重但有自己 KV pool），专门跑 草稿 (draft) forward。

2. 请求进入 – Prefill 阶段

2.1 Draft Req 的生成

Req.create_draft_request()

  • 建一个轻量 Req 镜像（req.draft_req），共享 rid，但：
    • origin_input_ids 与主 req 同步
    • 独立的 req.draft_output_ids / verified_token
    • KV 指针指向 draft_token_to_kv_pool

2.2 Chunked Prefill 的特殊处理

当启用 PD-分离且在 Decode 侧需要先收齐 KV，再校验 draft token：

chunk_verify_token_idx = len(prefix) + trunc_len

draft_req.verified_token = req.fill_ids[chunk_verify_token_idx]

3. GPU Forward – Speculative 组合batch

3.1 调度点

Scheduler.run_batch(batch)

3.2 EAGLEWorker.forward_batch_speculative_generation

  1. draft forward
    • 读 batch.spec_info (EagleDraftInput)，把上一轮 decode 的 verified token 拼到 prompt；
    • 得到 draft logits draft_ids (长度 = speculative_num_draft_tokens，常为 2)。
  2. 验证阶段 (target worker)
    • 把 [prompt + draft_ids[:-1]] 喂给 真实模型 (self.target_worker.forward_batch_generation)；
    • 将输出 token 与 draft 的最后一个 token 比对。
      • ① 若一致 → 全部 draft token 接受
      • ② 若不一致 → 只接受第一个，回滚第二个
  3. 返回值
    • next_token_ids：按校验后的最终输出组织
    • num_accepted_tokens：本轮真正写入 KV 的 token 数
    • 剩余 book-keeping（跳表更新、缓存指针移动）

forward_batch_speculative_generation
函数 细节 代码要点
draft() 小模型一次 forward speculative_num_steps (s) 步；每步取 topk 1. assign_draft_cache_locs CUDA kernel 在 draft-KV 里申请 bs × k × s slot
2. draft_forward() 循环：Flash/FI/Triton Attention → softmax → fast_topk3. 立即 token_to_kv_pool.free()，draft-KV 只暂存几毫秒
verify() 大模型只 forward 1 token 1. 把草稿 (d₀ … dₛ₋₁) 做成 EagleVerifyInput2. target_worker.forward_batch_generation(skip_sample=True)3. 只比较 最后 1 词 (dₛ₋₁ vs t₀)，得 accept_len ∈ {1, s}
forward_draft_extend_after_decode() 把“最后一个已接受 token” 写回 draft-KV，维持 position 单调 - prepare_extend_after_decode() 把新 token 拼在 hidden 后再 forward 一步
- 结束恢复 batch.seq_lens 等备份
finish_request() 回收两套 KV - target_tree_cache.cache_finished_req(req)- draft_tree_cache.cache_finished_req(req.draft_req, token_ids)

4. Scheduler 端结果处理

process_batch_result_decode()（和 prefill）

记录统计：self.spec_num_total_accepted_tokens, spec_accept_length 等。
Draft KV 生命周期：

  • self.draft_worker.finish_request() 在 req 结束/回收时同步释放 draft KV buffer。

5. 内存池 & TreeCache 交互

资源 主 KV Draft KV
Pool 对象 token_to_kv_pool draft_token_to_kv_pool
Cache tree_cache draft_tree_cache
申请 PrefillAdder / alloc_draft_buf 同步进行
释放 self.token_to_kv_pool.free() draft_worker.finish_request()
  • 两套 pool 地址空间分离，避免 draft-KV 撞主-KV
  • decode_mem_cache_buf_multiplier = 2 让 decode 侧一次 forward 可以直接复用 draft-KV

6. 退出 & 回滚路径

  • OOM Retract (ScheduleBatch.retract_decode)
    • 对 draft_pool 也走一遍释放流程。
  • Abort / Timeout
    • self.draft_worker.finish_request(req) 确保 draft-KV 清理

总结

时序图

  1. Scheduler 检测 --speculative_algorithm eagle → 派生 EAGLEWorker
  2. Prefill 阶段同时为 主 req 和 draft req 建 KV & PrefixCache
  3. 每轮 decode：
    1. draft_worker 草稿 → target_worker 校验
    2. 返回 next_ids + accepted_len
    3. Scheduler 累计吞吐，更新 req.state
  4. Draft KV 与主 KV 生命周期解耦，通过 finish_request() 统一释放
    整套逻辑保持 单活前向（draft+target 两次），但平均 ~2× 生成速率。

PD分离下的逻辑

Draft-model 的 prompt KV-cache 就是在 PD 分离架构的 Prefill Pod 里顺着 prompt 一起“预烤”出来的，并且在 Prefill 结束时随同 Target-model 的 KV 一起通过 Mooncake (or mock) 通道传给 Decode Pod。

下面把关键链路拆出来看看：

1. Prefill 阶段遇到 EAGLE 的分支

  • self.draft_worker 就是 EAGLEWorker，无论是在 P 还是 D 侧都会被创建。
  • 当前 batch 的 forward_mode == EXTEND（Prefill），于是 EAGLEWorker 走到 else 分支（见下一节）。

2. EAGLEWorker 在 Prefill 阶段做了什么

forward_draft_extend() 会

  1. 把 batch 的 memory-pool 指到 Draft-model 自己的 **token_to_kv_pool**；
  2. 执行一次 full-prompt forward，把所有 KV 写到 Draft-model 的 pool；
  3. 把 prompt 的 Draft-KV 引用挂在 batch.out_cache_loc 里备用。
    这样，Draft-model 的 prompt cache 就在 Prefill 端生成完成。

3. Prefill 端打包并发送两套 KV

  • kv_indices  → Target-model 那套 prompt-KV 的槽位索引
  • draft_kv_indices → Draft-model 那套 prompt-KV 的槽位索引
    ﻿send_kv_cache() 最终调用 MooncakeKVTransferAgent.send_kv_caches()，一次性把两套 KV copy 到 Decode Pod （若未启用 EAGLE 就把 draft part 设 None）。

4. Decode 侧加载

Decode Pod 在 load_cache() 里对称地

  • loc / draft_loc 分别指向 Target / Draft 的 KV-buffer，写完后两边的 KV 都已就绪，Draft-model 可以直接参与后续 草稿-验证 回路。

为什么一定要在 Prefill 端生成 Draft-KV？

目的 解释
Draft-model 第一次 decode 就要有 prompt 否则 D 侧还要再跑一遍 Prefill，白白浪费。
P、D 的 KV-pool 相互独立 Prefill 端分配好的 Draft 槽位必须原样搬到 D 侧，保持 index 对齐。
统一接口 send_kv_cache() / recv_kv_caches() 支持 (target, draft) 两路输入，关闭 EAGLE 时 draft 参数传 None 即可。

结论：在 PD-分离 + EAGLE 场景下，Prefill Pod 会同时生成 Target 与 Draft 的 prompt-KV，

然后一并传输到 Decode Pod；Decode Pod 拿到后就能立即开始 “一次 forward 草稿 2 token，验证最后 1 token” 的高速循环。
