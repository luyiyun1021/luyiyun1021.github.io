组件概览

Mooncake pd 分离组件分为以下几个

  • MooncakeKVManager: 只用于prefill，记录prefill和decode交互所用的信息，可以有很多种，decode会请求该信息和prefill进行连接

  • MooncakeKVSender: 负责初始化内存、Bootstrap server以及发送kv cache，prefill和decode都有，作为KV connector的管理器

  • MooncakeKVReceiver: 专属于prefill，发送kv cache

  • MooncakeKVBootstrapServer: 专属于decode，和prefill握手，获取bootstrap server的交互信息，接收kv cache

处理流程状态（类似于 tcp 握手的状态机）

  • Failed = 0

  • Bootstrapping = 1

  • WaitingForInput = 2

  • Transferring = 3 # no used

  • Success = 4

mini_lb(sglang提供的pd分离proxy server)

  • 对每个req，会生成一个随机int room id, 以及从候选prefill和decode实例中随机挑选一对获得prefill_config.url, prefill_config.bootstrap_port, decode_server, 并添加到原始的req中, 随后同时向prefill和deocde节点发送modified_req, 等待响应

整体流程

在原生 SGLang 调度事件循环之上，额外加入了 非阻塞的发送端（sender）与接收端（receiver）操作。

Prefill Server

  1. Bootstrap Queue

    1. 为每个请求初始化一个 sender

    2. 将尚未完成启动阶段（握手与显存预分配）的请求放入队列

    3. 轮询 sender，检测启动状态

    4. 启动完成后，将请求移至 Waiting Queue

  2. Waiting Queue

    1. 使用 PrefillAdder 弹出请求

    2. 执行 forward （Prefill 前向计算）

    3. 计算完毕后把请求加入 Infight Queue

  3. Infight Queue

    1. 非阻塞轮询该请求对应的 sender

    2. 传输完成后，将请求返回（标记为已完成）

Decode Server

  1. Prealloc Queue

    1. 为每个请求初始化一个 receiver

    2. 先完成握手；当有空闲 KV 显存时立即预分配

    3. 预分配完成后，将请求移入 Transfer Queue

  2. Transfer Queue

    1. 轮询 receiver，检查传输进度

    2. 传输完成后，将请求移入 Waiting Queue

  3. Waiting Queue

    1. 用队列中的请求构造 PrebuiltExtendBatch

    2. 跳过Prefill forward，只填充元数据

  4. Running Batch

    1. 将已解析的 PrebuiltExtendBatch 合并到运行批中，执行 Decode 阶段

初始化阶段

Prefill 节点

  • TokenizerManager 初始化

    • 启动 MooncakeKVBootstrapServer

  • MooncakeKVBootstrapServer 提供 /route 接口负责传递prefill的ip和port等信息

    • PUT /route（节点注册）

      • 接收：role、ip、port、rank

      • 计算 dp_group、tp_rank_in_dp_group

      • 存入 prefill_port_table[dp_group][tp_rank_in_dp_group]

    • GET /route（信息查询）

      • 根据 engine_rank 和 target_dp_group 从 prefill_port_table 获取节点信息

      • 若两参数均为 -1，返回 并行配置

  • Scheduler.init_disaggregation 中的初始化

    1. 实例化 PrefillBootstrapQueue（存放正在等待 Bootstrap 的请求）

      1. 实例化 MooncakeKVManager

        1. 调用 register_buffer_to_engine：

          • 将已分配的 KV cache 地址和 metadata 地址注册到 Transfer Engine

        2. 调用 start_prefill_thread：

          • 创建 ZMQ server socket，绑定空闲端口为 rank_port

          • 启动 bootstrap_thread，监听来自 Decode 的 pre-allocated 信号

          • 收到信号后，将对应请求的 request_status 设为 WaitingForInput

        3. 调用 _register_to_bootstrap：

          • 通过 PUT /route 向 Master（dist_init_addr）注册：role=PREFILL、tp_size、dp_size、本地 ip、rank_port、全局 rank

        4. 创建 transfer_queues（缓冲 KV 数据块），并启动 transfer_worker 消费线程

          • 数据流向：[KV 数据块] → add_transfer_request → transfer_queues → transfer_worker → 网络传输

        5. 创建 disagg_prefill_inflight_queue（存储正在发送 KV cache 的 Prefill 请求）

Decode 节点

  • Scheduler.init_disaggregation 中的初始化

    1. 实例化 DecodePreallocQueue（存放正在等待 pre-allocation 的请求）

      1. 实例化 MooncakeKVManager

        1. 调用 start_decode_thread：

          • 创建 ZMQ server socket，绑定空闲端口

          • 启动 decode_thread，接收 Prefill transfer_worker 同步的 room-id 状态（Success/Failed）

    2. 初始化 DecodeTransferQueue（存放正在拉取 KV cache 的请求）

Mooncake engine相关

初始化阶段，prefill和decode在KVManager都需要初始化一个Mooncake engine

infiniband device指的是nvidia的infiniband网卡，参考NVIDIA InfiniBand 网卡，支持GPUDirect RDMA。

mooncake的transfer engine的初始化：其一创建TransferMeta，用于管理mooncake的所有元数据，包含两个plugin

  • 基于rpc的handshake socket。

  • metadata storage管理plugin，元数据存储，可以是etcd、redis或者http，本地一般用redis即可。

其二创建MultiTransport，实现Mooncake的数据传输功能，支持tcp、rdma及nvmeof。

我们结合SGLang的源代码看，在初始化KVManager时，sglang会把已经分配的kv cache地址信息以及metadata的地址信息注册到Transfer Engine里，这一步prefill和decode的逻辑是一致的。

Transfer Engine调用的是Transport的注册方法，如果使用RDMA，则是将KV cache的物理地址和infiniband设备做一个映射。我们前面提到KV sender会并行地发送每层的KV cache，在prefill forward出一个chunk之后，调用KV sender的send方法将kv_indices发送给prefill的transfer thread，kv_indices的定义为

得到的是虚拟地址，即在物理地址上的索引，transfer thread调用send_kvcache，需要三个信息：kv chunk在prefill的虚拟地址、在decode上全局的kv物理地址、在decode上kv cache物理地址上的索引

send_kvcache会将prefill_kv_indices和dst_kv_indices做一个连续内存的聚类，连续的内存地址一次性发送

比如prefill_kv_indices=[1,2,3,5,6]，dst_kv_indices=[2,3,4,7,8]，则发送就是

transfer_sync(src=[1,2,3], dst=[2,3,4])和transfer_sync(src=[5,6], dst=[7,8])

每chunk prefill跑完一次性发送所有层的kv cache。前面提到在prefill最后一个chunk完成后，transfer engine还会发送一些辅助信息，这个辅助信就是prefill的第一个token id，decode收到后将其初始化到decode batch的output_ids结果里面

这里first token是交给Decode，等Decode做一次前向再统一返回给Proxy，所以TTFT的时间其实是Prefill+一次Decode，也就是说TTFT被Decode影响，如果Decode里因为资源问题还在排队那么当前请求的TTFT会显著上升。

总结来看，SGLang给出了一个标准的PD分离方案实现，prefill得到所有层的kv cache，然后一次性发送给decode，prefill的第一个token不会直接返回给proxy，而是交给decode继续处理。对于KV cache的存储，其实也是交给prefill和decode自己，尚未利用mooncake的store，也就是P2P的KV cache存储方案。

请求处理阶段

在scheduler中，prefill和decode分别会创建一个MooncakeKVSender和MooncakeKVReceiver与req绑定，KV receiver会从bootstrap server中得到prefill的ip和port，DP group和TP group都是一一对应的

一、Prefill 节点

1. 主流程（event_loop_normal_disagg_prefill）

  1. 接收新生成请求

    -﻿process_input_requests → handle_generate_request → disagg_prefill_bootstrap_queue.add

    • 为每个 Req 创建并绑定一个 MooncakeKVSender

      • 通过 kv_mgr 将对应的 bootstrap_room 状态更新为 Bootstrapping

    • 调用 _process_req：req.sampling_params.max_new_tokens = 1

    • 把 Req 添加到 disagg_prefill_bootstrap_queue

  2. Bootstrap 阶段轮询

    • 调用 BootstrapQueue.pop_bootstrapped

    • 对每个 Req 调用其 KVSender.poll，从 kv_mgr.check_status(bootstrap_room) 获取状态

    • 仅当状态为WaitingForInput 时：

      • 初始化该 KVSender（设置 num_kv_indices、metadata_buffer_index）

      • 将 Req 移动到 waiting_queue

  3. 分块 Prefill 并发送 KV

    • 在 process_prefill_chunk 中处理：

      • 如果上一个 batch 中有 chunked_req：

        • 将它从 last_batch 中移出

        • 缓存到 Radix Cache

        • 调用 send_kv_chunk，把 req_to_token[req.req_pool_idx, start_idx:end_idx] 对应的 KV 索引发送到 Decode Server

      • KV Transfer 结束条件：

        • 每执行完一个 chunk，Prefill Scheduler 会调用 send_kv_chunk，由 KVSender 多线程一次性发送所有 layer 的 KV cache

        • 在最后一个 chunk，Sender 会额外发送辅助数据，并把 room id + 状态 Success 发送给 Decode 的监听线程

    • MooncakeKVSender.send 的实现要点：

      • 调用 kv_mgr.add_transfer_request

      • 创建 TransferKVChunk，放入 transfer_queue

      • TransferKVChunk 包含 room、prefill_kv_indices、index_slice、is_last 和 prefill_aux_index

  4. 获取新 Prefill Batch

    • 调用 get_new_batch_prefill 从 waiting_queue 中获得 Prefill 请求

    • 为即将处理的请求创建 ScheduleBatch

  5. 模型前向执行

    • Scheduler 调用 run_batch，将 ScheduleBatch 转换为 ModelWorkerBatch

    • 调用 TpModelWorker.forward_batch_generation，等待 logits_output 和 next_token_ids

  6. Batch 结果处理

    • 调用 process_batch_result_disagg_prefill：

      • 调用 send_kv_chunk 传输完成 Prefill 的请求

      • 锁定 Radix Tree

      • 将请求加入 disagg_prefill_inflight_queue

  7. 监控 Inflight 队列

    • 调用 process_disagg_prefill_inflight_queue：

      • 对每个请求执行 KVSender.poll，通过 kv_mgr.check_status(bootstrap_room) 获取状态

      • 如果状态为 Success：

        • 从队列中拿出请求

        • 解锁 Radix Tree

        • 调用 stream_output 返回结果给 Detokenizer

2. bootstrap_thread

  • 接收 Decode 节点在 KVReceiver 初始化阶段和 disagg_decode_prealloc_queue.pop_preallocated 阶段发送的握手信息

    • 如果 room ID = None：

      • 将握手信息解析为 KVArgsRegisterInfo，存入 decode_kv_args_table

    • 如果 room ID != None：

      • 将握手信息解析为 TransferInfo，存入 transfer_infos[room]

      • 当该 TP rank 收到所有需要发送 KV cache 的 Decode 节点握手后，调用kv_mgr.update_status(bootstrap_room, WaitingForInput)

3. transfer_worker

  • 处理 Prefill 节点在 process_prefill_chunk 和 process_batch_result_disagg_prefill 阶段放入 transfer_queue 的传输任务

  • 从 transfer_queue 中取出 TransferKVChunk

    • 读取该请求的 transfer_infos（包含 Decode 端的 mooncake_session_id、KV 索引、物理地址，以及 Prefill 端的索引）

  • 发送 KV Cache：

    • 调用 send_kvcache：按 layer 提交 engine.batch_transfer_sync 任务，底层调用 batch_transfer_sync_write

  • 如果 kv_chunk.is_last：

    • 调用 send_aux → engine.batch_transfer_sync

    • 通过 kv_mgr.update_status(bootstrap_room, Success)

    • 调用 sync_status_to_decode_endpoint，向 Decode 线程同步 room id 的状态（Success/Failed）

二、Decode 节点

1. 主流程（event_loop_normal_disagg_decode）

  1. 接收新生成请求

    -﻿process_input_requests → handle_generate_request → disagg_decode_prealloc_queue.add

    • 为每个 Req 创建并绑定一个 MooncakeKVReceiver

      • 通过 kv_mgr 将 bootstrap_room 状态更新为 Bootstrapping

      • 调用 _get_prefill_parallel_info_from_server：

        • 通过 /route 获取 Prefill 的 tp_size、dp_size，并存入 kv_mgr.prefill_tp_size_table

        • 计算并设置 target_tp_ranks（支持三种 TP 配置策略）

          • local_tp_size_per_dp_rank == prefill_tp_size_per_dp_rank: Prefill-Decode 一对一模式, Decode端需要收到一个tp_rank发来的kv cache会把Req设为Success状态, Prefill端需要发送kv cache给一个tp_rank会把Req设为Success状态

          • local_tp_size_per_dp_rank > prefill_tp_size_per_dp_rank: Prefill-Decode 一对多模式, Decode端需要收到一个tp_rank发来的kv cache会把Req设为Success状态, Prefill端需要发送kv cache给多个tp_rank才会把Req设为Success状态(required_dst_info_num != 1)

          • local_tp_size_per_dp_rank < prefill_tp_size_per_dp_rank: Prefill-Decode 多对一模式, Decode端需要收到多个tp_rank发来的kv cache才会把Req设为Success状态(required_prefill_response_num != 1), Prefill端需要发送kv cache给一个tp_rank会把Req设为Success状态

          • 目前只在 mla 模型中支持 decode 和 prefill tp 配置不同, 对于 mla 模型, 我们可以只从一个 prefill 节点获取 KV 缓存，但仍需要在连接池中维护多个连接，并且必须向其他 prefill 节点发送空请求，否则 KVPoll 状态将无法正确设置

      • 构造 bootstrap_key = "{bootstrap_addr}_{target_dp_group}_{target_tp_rank}"

      • 从 /route 查询对应 Prefill 节点的 IP/port，缓存到 kv_mgr.connection_pool[bootstrap_key]

      • 调用 _register_kv_args，向 Prefill 节点发送初始化信息（包含 room ID=None、decode IP/port、session ID、KV cache pool 地址、MetadataBuffers 地址）

      • 通过 kv_mgr.update_status(bootstrap_room, WaitingForInput)

  2. Pre-allocation 阶段

    • 调用 disagg_decode_prealloc_queue.pop_preallocated：

      • KVReceiver.poll → kv_mgr.check_status(bootstrap_room) → 将所有 WaitingForInput 的请求标记 waiting_for_input=True

      • 调用 _pre_alloc，为每个请求分配 req_to_token 和 token_kv_pool 空间

      • 调用 KVReceiver.init，向 Prefill 的 bootstrap_thread 发送五个信息：room ID, decode IP/port, session ID, kv cache 索引, first token 的输出位置

  3. Transfer 拉取阶段

  • 将预分配完成的请求加入 disagg_decode_transfer_queue

    • 调用 disagg_decode_transfer_queue.pop_transferred：

      • 对每个请求执行 KVReceiver.poll → kv_mgr.check_status

      • 对于 Success 状态的请求，使用 metadata_buffer_index 获取 output_id 等元数据，并移出队列

      • 将传输完成的请求加入 waiting_queue

  1. Batch 构建与执行

    • 调用 get_next_disagg_decode_batch_to_run：

      • 从 waiting_queue 中获取已完成传输的请求

      • 调用 get_new_prebuilt_batch 创建“伪 Prefill” ScheduleBatch

        • 第一 token 交给 Decode，Decode 再执行一次前向后统一返回给 Proxy

      • 若 waiting_queue 为空，则将之前的伪 Prefill Batch 合并至当前 Running Batch，继续 continuous batching

    • Scheduler 调用 run_batch → TpModelWorker.forward_batch_generation，等待 logits_output 与 next_token_ids

  2. 解码结果处理

    • 调用 process_batch_result_decode：

      • 通过 check_finished 验证请求完成状态

      • 未完成的继续循环，完成的调用 tree_cache.cache_finished_req(req) 并 stream_output

2. decode_thread

  • 监听 Prefill 节点的 transfer_worker 在最后一个 chunk 时同步的 room id + 状态（Success/Failed）

  • 当收到预期数量的 Success 响应后，调用kv_mgr.update_status(bootstrap_room, Success)
