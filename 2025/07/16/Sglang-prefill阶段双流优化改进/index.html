    Sglang prefill阶段双流优化改进

    发表于 2025-07-16 更新于 2025-08-20 分类于 大模型 ， 推理技术 ， Sglang 阅读次数： 本文字数： 1.1k 阅读时长 ≈ 4 分钟

    背景

    由于prefill是算力瓶颈且线上服务有ttft的限制, batch size通常不会太大, 对于token长度为千数量级的, 通常在1-4之间, 那么当batch size为奇数或者batch内请求的长度不均时, 原始的split batch做双流的方式, 很容易会造成两个batch的计算和通信不均衡, 影响双流的效果, 因此考虑更加细粒度的split token方式, 缓解这种情况

    选择逻辑（在 split_prefill_forward_batch 中）

    选择标准

    THRESHOLD：令牌分布阈值（0.4）

    如果按batch拆分能够实现相对均衡的token分布，则使用简单的batch拆分, 否则使用复杂但更精确的token拆分

    Split Token 详细拆分逻辑解析

    概述

    split_tokens_for_prefill_overlap 函数实现了按令牌数量将批次拆分为两部分的复杂逻辑。这种拆分方式可能会将一个序列分割到两个处理单元中，以实现更精确的负载均衡。

    拆分过程详解

    1. 确定拆分点

    核心逻辑：

    • batch_split_index：需要被拆分的序列在批次中的索引

    • split_index_extend_token_part1：该序列中分配给第一部分的令牌数量

    • split_index_extend_token_part2：该序列中分配给第二部分的令牌数量

    示例：

    2. 计算批次大小

    逻辑说明：

    • 第一部分包含：完整的前 batch_split_index 个序列 + 被拆分序列的前半部分

    • 第二部分包含：被拆分序列的后半部分 + 完整的后续序列

    3. 拆分请求池索引

    注意： 被拆分的序列在两个部分中都有对应的请求索引。

    4. 处理序列长度 (extend_seq_lens)

    关键点：

    • 修改第一部分的最后一个序列长度

    • 修改第二部分的第一个序列长度

    • 这两个修改的是同一个原始序列的不同部分

    5. 拆分令牌相关数据

    说明： 按照第一部分的令牌数量切分实际的令牌数据。

    6. 处理前缀长度 (extend_prefix_lens)

    核心逻辑：

    • 第一部分的前缀长度保持不变

    • 第二部分的第一个序列（被拆分序列的后半部分）的前缀长度需要增加第一部分已处理的令牌数

    为什么要调整前缀长度？

    • 前缀长度表示已经在KV缓存中的令牌数量

    • 被拆分序列的后半部分在处理时，前面的部分已经被第一部分处理了

    • 所以需要更新前缀长度以反映这个状态

    7. 重新计算总序列长度 (seq_lens)

    公式：seq_lens = extend_prefix_lens + extend_seq_lens

    这个公式反映了序列的总长度 = 前缀长度（已缓存） + 扩展长度（需要处理）

    8. 重新计算位置信息 (extend_start_loc)

    说明：

    • 第一部分可以直接使用原始的位置信息

    • 第二部分需要重新计算，因为序列结构发生了变化
